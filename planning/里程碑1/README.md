# 里程碑1：最小可运行 Agent

## 目标

通过浏览器打开本地网页，与一个最小 Agent 交互：在网页输入任务，由模型选择工具，本地执行工具，将真实结果交回模型，再由模型继续行动或给出最终回答，并在网页显示过程和结果。会话记录保存在本机磁盘上，重启后仍可在浏览器中查看。

前三步依次完成聊天页面、模型服务和 SSE 流式串联；第四步定义工具，第五步跑通一次工具调用，第六步补齐失败与停止处理，第七步支持连续多轮工具调用，第八步完成本地存储与历史回看。

## 交互方式

客户端采用本地网页。网页负责接收输入和显示运行过程；本地 Agent 程序负责组装上下文和执行工具，其中的模型服务负责向模型发送请求。模型密钥只由本地程序持有，不放入网页，也不随网页响应返回。

模型服务默认使用 `deepseek-flash`，通过 OpenAI SDK 的 Chat Completions 接口向 DeepSeek 提供的模型发送请求。模型标识和 SDK 调用方式参考 [DeepSeek 官方接入说明](https://api-docs.deepseek.com/)。

第三步打通的链路是：网页发送消息 → 本地模型服务通过 OpenAI SDK 取得模型的流式回复 → 通过 SSE 将片段推回网页 → 网页逐段追加到同一条回复中。SSE 指服务端保持连接，持续把新消息推送给页面；流式请求方式参考 [OpenAI Docs](https://developers.openai.com/api/docs/guides/streaming-responses)。

首版仅供本机使用；未指定的界面框架与运行环境在实现前讨论。

参考 [Pi 的运行事件设计](../../pi/packages/agent/README.md#event-flow)，将 Agent 运行与界面展示分开。相比原先的终端方案，本方案增加网页与本地程序之间的通信，核心循环仍按原有目标逐步构建。

## 范围

| 职责 | 本里程碑需要做到 |
| --- | --- |
| 上下文组装 | 整理任务说明、用户输入、历史消息和工具说明，形成每轮模型请求 |
| 模型调用 | 默认通过 OpenAI SDK 请求 `deepseek-flash`，取得流式文字回复或完整的工具调用请求 |
| 工具执行 | 提供一个 `read_file` 工具，校验名称和参数，读取指定工作目录内的文本文件并返回真实结果 |
| 控制循环 | 将模型的工具调用及对应结果加入历史，再次调用模型；管理继续和停止条件 |
| 本地存储 | 按会话保存消息、工具调用、执行结果和运行状态，重启后仍可读取 |
| 网页交互 | 提供任务输入、发送、运行状态、结果显示和停止操作；通过 SSE 逐段展示回复，并展示工具名称、参数、执行结果及最终回答；支持查看历史会话 |

先用简单函数打通这些职责，按需要再调整结构。工具调用可以使用模型原生能力，无须额外解析文本形式的 Thought/Action/Observation。网页先用简单的聊天界面，以文字展示运行记录和回复；SSE 流式显示是第三步的完成条件。

## 推进步骤

### 第一步：建立基本的聊天页面

- [ ] 提供本地网页的输入框、发送操作和消息列表；能够打字、发送消息，并将发出的消息显示在列表中。
- 验收：用浏览器打开页面，输入一句话并发送，能看到自己发送的消息，继续输入和发送也能正常显示。这一步先验证聊天页面，不接入真实模型，也不伪造模型回复。
- 技术设计：[Feature1：建立基本的聊天页面](./feature1-基本聊天页面.md)（待整体批准；尚未实现）。

### 第二步：跑通模型服务

- [ ] 在本地程序中提供可以独立调用的模型服务，默认使用 `deepseek-flash`，通过 OpenAI SDK 向 DeepSeek 发送消息、取得真实回复；密钥由本地程序持有。
- 验收：通过独立请求或最小自检发送一句话，能取得真实模型回答；请求失败时明确返回错误。这一步不依赖网页，先单独确认模型服务可用。

### 第三步：通过 SSE 打通客户端与模型服务

- [ ] 将网页发送的消息交给本地模型服务，开启模型流式返回；本地服务通过 SSE 将收到的文本片段推送给网页，由网页逐段拼接显示，并区分生成中、完成和出错状态。
- 验收：在网页输入一句话并发送，回答在生成过程中逐段出现，而非等待整段完成后一次性显示；结束后完整回复保留在消息列表中。连接或模型调用失败时页面显示错误并退出等待；网页及其收到的响应中不包含模型密钥。

### 第四步：建立基本的工具定义

- [ ] 定义 `read_file` 的名称、用途和参数要求，区分给模型看的工具说明与本地真正执行的函数；将工具说明放入模型请求，并能从流式返回中收齐、识别完整的工具名称和参数。
- 验收：模型请求中包含工具定义；模型提出读取请求时，能在网页看到工具名称和文件路径。这一步暂不执行工具。

### 第五步：跑通一次工具调用

- [ ] 收到完整的工具调用后，由本地 Agent 程序校验并执行，将工具调用及其关联的真实结果加入历史，再调用一次模型，让它根据结果回答，并在网页展示全过程。不执行尚未收齐的流式工具参数。
- 验收：模型请求读取文件，本地读取成功，下一次模型请求包含工具调用及对应结果，最终回答符合文件内容。本步骤只验证一次工具执行和结果回传，连续多轮调用留到第七步。

### 第六步：验证失败和停止条件

- [ ] 将文件不存在、未知工具和无效参数等工具错误交回模型；模型请求失败时明确结束，不进行无限重试。
- [ ] 为模型请求和工具执行设置超时，为后续循环准备模型调用总轮数上限；提供网页停止操作，将停止请求传给本地 Agent 程序。
- 验收：工具失败时能返回真实错误；单次调用一直不返回时能超时结束等待；SSE 异常断开时不误报为正常完成；达到上限或用户点击停止后，本地 Agent 程序不再发起新的模型调用或执行工具，网页显示停止原因。先通过模拟失败、超时和连续调用请求验证这些保护，第七步再验证它们在完整循环中生效。

### 第七步：建立基本的 ReAct 循环

- [ ] 将“调用模型 → 执行工具 → 回填结果 → 再调用模型”接成循环。每轮根据模型回复决定继续调用工具还是结束回答，并始终遵守第六步的失败和停止规则。
- 验收：模型能根据第一次工具返回的线索，再次决定调用工具；至少经过两轮先后发生的工具调用后给出最终回答。网页展示各轮调用和结果；正常回答能够结束，持续请求工具或持续失败也会受到上限约束。

### 第八步：本地存储与历史回看

- [ ] 由本地程序将会话记录写入本机磁盘，保存会话标识、时间、完整的用户消息和模型消息、工具调用及对应结果、运行状态。完成一条记录就保存，不等整次任务结束；模型密钥不写入会话记录。保存格式在实现前讨论，可参考 [Pi 的会话存储设计](../../pi/packages/coding-agent/docs/sessions.md#control-session-storage)。
- [ ] 浏览器提供历史会话列表，选择后可以查看已保存的消息、工具调用、执行结果和运行状态；历史展示从本地存储读取，不依赖当前页面内存中的消息。
- 验收：刷新页面、关闭并重开浏览器、重启本地服务后，已保存记录仍能按原顺序查看，不重复、不互相覆盖。运行中断后能查看已保存部分，并标明中断状态；保存失败时明确显示未保存，保留已有记录。回看历史不会重新调用模型或执行工具。

## 整体验收

每个案例从新的任务历史开始，不携带其他案例的对话或文件内容。

### 页面、模型服务与 SSE（第一至第三步）

先分别验证页面可以输入、发送和显示消息，模型服务可以通过 OpenAI SDK 独立请求 `deepseek-flash`；再将两者串联，确认真实回复通过 SSE 逐段显示，并有明确的完成或错误状态。不能用预先准备好的文本代替真实模型返回来通过第三步验收。

### 单轮工具调用（第五步）

准备一个文本文件 `note.txt`，内容为 `项目名称：青禾`，只把文件路径交给 Agent。

用户在本地网页输入并发送：

> 读取 note.txt，告诉我里面记录的项目名称。

验收通过应能在网页观察到：

1. 模型请求调用 `read_file`，参数指向 `note.txt`。
2. 本地程序读取文件，返回 `项目名称：青禾`。
3. 工具调用及结果进入下一轮上下文，模型回答项目名称是“青禾”。
4. 换成另一个项目名称后，回答随文件内容变化。

### 多轮工具调用（第七步）

再准备 `index.txt`，内容为 `项目信息见 note.txt`。在网页输入：

> 读取 index.txt，按照其中的线索找到项目名称。

验收：模型先读取 `index.txt`，收到结果后再请求读取 `note.txt`，最后回答“青禾”。记录中应有至少两轮先后发生的工具调用，每次结果都进入下一轮上下文；不将一次回复中同时提出的多个工具请求算作多轮决策。

### 本地存储与历史回看（第八步）

完成上述多轮工具调用后，刷新网页并重启本地服务，再从历史会话列表打开该次任务。确认两轮工具调用、对应结果和最终回答都能显示，且查看过程不产生新的模型请求或工具执行。再验证任务中断和保存失败时的提示与已有记录保护。

用真实模型跑通 SSE 流式回复、单轮和多轮工具调用案例，并用简单测试或断言检查文本片段拼接、完成与错误状态、工具结果回填、工具失败、超时、轮数上限、用户停止、存储读写一致性和重启后历史回看；不只根据最终回答判断闭环是否成立。

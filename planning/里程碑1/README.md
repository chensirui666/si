# 里程碑1：最小可运行 Agent

## 目标

通过浏览器打开本地网页，与一个最小 Agent 交互：在网页输入任务，由模型选择工具，本地执行工具，将真实结果交回模型，再由模型继续行动或给出最终回答，并在网页显示过程和结果。会话记录保存在本机磁盘上，重启后仍可在浏览器中查看。

第一步“建立基本的聊天页面”已完成并合并。原第二、三步合并为新的第二步“单会话流式聊天”，在已有页面上接入模型服务、基础模型设置和 WebSocket 流式显示。第二步的所有聊天内容归属于唯一的当前对话，不引入会话列表、切换或多会话管理。原第四至第八步依次减一，成为第三至第七步：定义工具、跑通一次工具调用、补齐失败与停止处理、支持连续多轮工具调用、完成本地存储与历史回看。

## 交互方式

客户端采用本地网页。网页负责接收输入、配置模型密钥和显示运行过程；本地 Agent 程序负责组装上下文和执行工具，其中的模型服务负责向模型发送请求。密钥由本地程序保存与使用；网页仅在配置时短暂持有用户新输入的密钥，保存后不保留、不写入浏览器持久化存储。后端不向网页返回已保存的密钥，日志、状态查询和聊天响应也不包含密钥。

模型服务默认使用 `deepseek-flash`，通过 OpenAI SDK 的 Chat Completions 接口向 DeepSeek 提供的模型发送请求。模型标识和 SDK 调用方式参考 [DeepSeek 官方接入说明](https://api-docs.deepseek.com/)。

模型到后端采用 SSE 流式返回，由 OpenAI SDK 解析；后端到网页采用 WebSocket，连接、订阅和后台任务的生命周期参考本地 dsh 源码。本期直接打通：网页发送消息 → HTTP 确认接收 → 后端调用模型并接收 SSE 流式回复 → 本地服务通过 WebSocket 推送回复片段和运行状态 → 网页逐段追加到同一条回复中。模型模块与传输通道可以分层测试，交付以真实网页聊天链路为准。模型流式响应机制参考 [OpenAI Docs](https://developers.openai.com/api/docs/guides/streaming-responses)。

首版仅供本机使用；未指定的界面框架与运行环境在实现前讨论。

参考 [Pi 的运行事件设计](../../pi/packages/agent/README.md#event-flow)，将 Agent 运行与界面展示分开。相比原先的终端方案，本方案增加网页与本地程序之间的通信，核心循环仍按原有目标逐步构建。

## 范围

| 职责 | 本里程碑需要做到 |
| --- | --- |
| 上下文组装 | 整理任务说明、用户输入、历史消息和工具说明，形成每轮模型请求 |
| 模型调用 | 默认通过 OpenAI SDK 请求 `deepseek-flash`，取得流式文字回复或完整的工具调用请求 |
| 工具定义与调用接收 | 参考 Pi，本期仅统一定义 `read`、`bash`、`edit`、`write` 四种工具，从后端 Model 函数接口接入和验收，默认提供四种声明并收齐调用供后续消费；其他工具暂不纳入 |
| 工具执行 | 校验名称和参数，以 `read` 读取指定工作目录内的文本文件并返回真实结果 |
| 控制循环 | 将模型的工具调用及对应结果加入历史，再次调用模型；管理继续和停止条件 |
| 本地存储 | 按会话保存消息、工具调用、执行结果和运行状态，重启后仍可读取 |
| 网页交互 | 提供任务输入、发送、运行状态、结果显示和停止操作；通过 WebSocket 逐段展示回复，并展示工具名称、参数、执行结果及最终回答；支持查看历史会话 |

先用简单函数打通这些职责，按需要再调整结构。工具调用可以使用模型原生能力，无须额外解析文本形式的 Thought/Action/Observation。网页先用简单的聊天界面，以文字展示运行记录和回复；通过 WebSocket 逐段显示真实回复是第二步的完成条件。

### 第二步：单会话流式聊天

原第二、三步合并为本步，在已完成的第一步基础上交付能实际与 DeepSeek 聊天的网页；模型服务与流式显示不再分开交付，相关职责仍可分别设计和测试。当前只存在唯一的当前对话，所有内容在这段对话中展示；会话列表、切换与多会话管理不属于本步范围。后端持有当前对话，刷新或重连后恢复内容。本步先等待当前回答结束再接受下一次发送，支持生成期间继续发送并排队已记为后续待办。

- 当前对话的用户消息、模型回复和运行状态由后端内存统一持有；网页持有输入草稿和展示状态。后端从当前对话准备模型输入，同一后端下的多个浏览器页面共享当前对话。
- WebSocket 建联后先接收当前内容与生成状态，再接收后续增量；刷新或重连从仍运行的后端恢复。关闭网页不自动取消生成。后端重启后内存聊天清空，已保存的凭据文件仍保留；聊天磁盘持久化按第七步推进。
- 本期生成期间可以继续编辑草稿，发送按钮暂不可用；后端也拒绝并发提交，当前生成完成或失败后恢复发送。这是为先跑通主线而接受的简化；用户期望后续改为允许继续发送、由后端依次处理，见[消息排队待办](../设计妥协记录.md#4-生成期间暂不支持排队发送)。相同内容在后续正常发送时仍作为新调用，不做去重。

- [ ] 在第一步已完成的 `web/` 基础聊天页上接入完整聊天，保留已确认的输入、发送、原文与阅读位置规则；扩展展示模型回复，并区分生成中、完成和出错状态。[第一步设计](./feature1-基本聊天页面.md)作为输入与展示行为参考。
- [ ] 使用 Node.js + TypeScript 与原生 `node:http` 建立本地后端。网页通过 HTTP 提交消息，HTTP 确认接收；后端持有本次调用的运行状态和已生成内容，通过 WebSocket 推送片段及最终结果，网页逐段追加到同一条回复中。连接与订阅参考 dsh，按本期唯一当前对话的范围收敛；后台任务独立执行，接收确认与执行结果分开，连接或订阅结束不等于取消任务。
- [ ] 模型模块默认通过 OpenAI SDK 的 Chat Completions 接口请求 `deepseek-flash`，接收 SSE 流式回复；接收后端调用方为本次请求准备的消息列表，不自行读取、保存或累加会话历史；将 SDK 响应转换为项目定义的模型事件流，网络封装归 HTTP/WebSocket 接入。
- 模型流的结束事件采用 Pi 的区分方式：`done` 表示正常终止，`error` 表示失败或取消，通过结束原因区分具体结果；一次模型调用结束不等于后续 Agent 整个任务完成。模型调用不自动重试，显式关闭 SDK 的自动重试；一次请求失败就返回 `error`，临时故障由调用方重新发起。
- 不做提交去重：用户再次发送相同内容，按新的一次正常提交与模型调用处理，不按文本或提交编号合并、复用先前调用。消息编号仅用于标识和更新对应消息，不作为去重依据。
- [ ] 凭据管理采用 B：凭据文件按 Pi 的 JSON 形式组织，保存在本机应用用户数据目录；读写和更新机制参考 dsh。本地配置命令与网页配置入口复用后端凭据读写，覆盖保存、更换、删除和查询非敏感配置状态，后续模型请求使用更新后的凭据。
- [ ] 聊天页增加左侧栏，底部放“设置”；点击后打开设置弹窗，进入“模型”，通过“添加提供方”选择 DeepSeek，输入 API Key 并保存。当前只支持 DeepSeek，默认模型仍为 `deepseek-flash`；已有配置可再次编辑，页面提供基础保存状态与明确错误反馈。参考[用户提供的设置界面](./assets/feature2-模型设置参考.png)，按简单、完整、可实际使用的要求覆盖这条配置流程。
- 验收：浏览器打开应用，经“设置 → 模型 → 添加提供方 → DeepSeek”保存 API Key，回到聊天页发送消息，取得真实模型回复，且回复在生成过程中通过 WebSocket 逐段出现，最终明确进入完成或出错状态。更换凭据后下一次调用使用新值，重启后仍能读取已保存的凭据；页面不读回已保存的密钥，保存或模型调用失败时明确反馈；“已配置”不冒充真实调用验证。模型和通道的独立检查用于支撑验收，不代替这条完整网页链路。

### 第三步：建立工具定义与调用接收

- 状态：需求、关键决策和两个模块已确认，技术设计待整体批准，见 [Feature3：工具定义与调用接收](./feature3-工具定义与调用接收.md)。实现与测试尚未开始。
- [ ] 参考 Pi 引入统一的工具定义与模型接入方式，本期仅定义 `read`、`bash`、`edit`、`write` 四种工具，参数约定直接沿用 Pi；`grep`、`find`、`ls`、`powershell` 暂不定义。各工具均能定义自己的名称、用途和参数要求，区分给模型看的说明与本地执行职责。
- [ ] 在后端工具接入入口，由调用方默认将这四种工具的说明放入 `ModelContext.tools`，接收模型返回的工具调用信息，收齐、整理完整的工具名称和参数，供后续模块消费。普通网页聊天暂不接入工具流程，留到后续执行阶段串联。
- 验收：直接调用后端 Model 函数接口，用独立上下文发起真实模型请求，确认四种工具均能正常定义并提供给模型，后端能正确取得模型真实返回的完整工具名称和参数。本步暂不执行工具，不通过网页工具流程验收。具体职责、接口和测试落点见技术设计；全部验收待实施。

### 第四步：跑通一次工具调用

- [ ] 收到完整的工具调用后，由本地 Agent 程序校验并执行，将工具调用及其关联的真实结果加入历史，再调用一次模型，让它根据结果回答，并在网页展示全过程。不执行尚未收齐的流式工具参数。
- 验收：模型请求读取文件，本地读取成功，下一次模型请求包含工具调用及对应结果，最终回答符合文件内容。本步骤只验证一次工具执行和结果回传，连续多轮调用留到第六步。

### 第五步：验证失败和停止条件

- [ ] 将文件不存在、未知工具和无效参数等工具错误交回模型；模型请求失败时明确结束，不进行无限重试。
- [ ] 为模型请求和工具执行设置超时，为后续循环准备模型调用总轮数上限；提供网页停止操作，将停止请求传给本地 Agent 程序。
- 验收：工具失败时能返回真实错误；单次调用一直不返回时能超时结束等待；模型 SSE 或网页 WebSocket 异常断开时不误报为正常完成；达到上限或用户点击停止后，本地 Agent 程序不再发起新的模型调用或执行工具，网页显示停止原因。先通过模拟失败、超时和连续调用请求验证这些保护，第六步再验证它们在完整循环中生效。

### 第六步：建立基本的 ReAct 循环

- [ ] 将“调用模型 → 执行工具 → 回填结果 → 再调用模型”接成循环。每轮根据模型回复决定继续调用工具还是结束回答，并始终遵守第五步的失败和停止规则。
- 验收：模型能根据第一次工具返回的线索，再次决定调用工具；至少经过两轮先后发生的工具调用后给出最终回答。网页展示各轮调用和结果；正常回答能够结束，持续请求工具或持续失败也会受到上限约束。

### 第七步：本地存储与历史回看

- [ ] 由本地程序将会话记录写入本机磁盘，保存会话标识、时间、完整的用户消息和模型消息、工具调用及对应结果、运行状态。完成一条记录就保存，不等整次任务结束；模型密钥不写入会话记录。保存格式在实现前讨论，可参考 [Pi 的会话存储设计](../../pi/packages/coding-agent/docs/sessions.md#control-session-storage)。
- [ ] 浏览器提供历史会话列表，选择后可以查看已保存的消息、工具调用、执行结果和运行状态；历史展示从本地存储读取，不依赖当前页面内存中的消息。
- 验收：刷新页面、关闭并重开浏览器、重启本地服务后，已保存记录仍能按原顺序查看，不重复、不互相覆盖。运行中断后能查看已保存部分，并标明中断状态；保存失败时明确显示未保存，保留已有记录。回看历史不会重新调用模型或执行工具。

每个案例从新的任务历史开始，不携带其他案例的对话或文件内容。

### 单会话流式聊天（第二步）

从实际网页入口开始，配置 DeepSeek API Key 后发送消息，确认后端通过 OpenAI SDK 接收真实模型 SSE 回复，网页通过 WebSocket 逐段显示，并有明确的完成或错误状态。所有内容只属于唯一的当前对话，能继续在同一聊天页发送和查看回复。不能用预先准备的文本或仅有独立模型请求成功来替代完整链路验收。输入、模型事件转换与传输边界仍在足以验证对应行为的较低层测试中检查。

### 单轮工具调用（第四步）

准备一个文本文件 `note.txt`，内容为 `项目名称：青禾`，只把文件路径交给 Agent。

用户在本地网页输入并发送：

> 读取 note.txt，告诉我里面记录的项目名称。

验收通过应能在网页观察到：

1. 模型请求调用 `read`，参数指向 `note.txt`。
2. 本地程序读取文件，返回 `项目名称：青禾`。
3. 工具调用及结果进入下一轮上下文，模型回答项目名称是“青禾”。
4. 换成另一个项目名称后，回答随文件内容变化。

### 多轮工具调用（第六步）

再准备 `index.txt`，内容为 `项目信息见 note.txt`。在网页输入：

> 读取 index.txt，按照其中的线索找到项目名称。

验收：模型先读取 `index.txt`，收到结果后再请求读取 `note.txt`，最后回答“青禾”。记录中应有至少两轮先后发生的工具调用，每次结果都进入下一轮上下文；不将一次回复中同时提出的多个工具请求算作多轮决策。

### 本地存储与历史回看（第七步）

完成上述多轮工具调用后，刷新网页并重启本地服务，再从历史会话列表打开该次任务。确认两轮工具调用、对应结果和最终回答都能显示，且查看过程不产生新的模型请求或工具执行。再验证任务中断和保存失败时的提示与已有记录保护。

用真实模型跑通模型 SSE 与网页 WebSocket 的流式链路、单轮和多轮工具调用案例，并用简单测试或断言检查文本片段拼接、完成与错误状态、工具结果回填、工具失败、超时、轮数上限、用户停止、存储读写一致性和重启后历史回看；不只根据最终回答判断闭环是否成立。

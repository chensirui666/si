# 里程碑1：最小可运行 Agent

## 目标

通过浏览器打开本地网页，与一个最小 Agent 交互：在网页输入任务，由模型选择工具，本地执行工具，将真实结果交回模型，再由模型继续行动或给出最终回答，并在网页显示过程和结果。同一会话支持手动和自动压缩上下文，能连续完成至少两次压缩、核对 token 下降并继续原任务。支持新建和切换不同 Session（会话），各自的消息、模型上下文、压缩记录与运行状态互相隔离。会话开始工作时，能够读取所属项目文件中的基础信息并纳入模型上下文，带着项目背景与必要约定开展工作。会话记录保存在本机磁盘上，重启后仍可在浏览器中查看。

第一步“建立基本的聊天页面”已完成并合并。第二步“单会话流式聊天”合并原第二、三步，并按三个子阶段分别设计、实施和验收：打开授权与订阅、凭据配置与本地模型发现、提交生成与实时展示。第二至第七步沿用唯一当前对话，第八步引入工作区和会话的独立管理，支持会话列表、切换和隔离。2026-11-05 按用户要求增加第七步上下文压缩；2026-11-09 增加第八步基础 Session 机制及第九步项目说明加载与启动上下文，本地存储与历史回看顺延为第十步。当前共十步：第三步定义工具与接收调用、第四步跑通八种工具的单轮执行、第五步支持用户停止当前调用、第六步支持连续多轮工具调用、第七步建立基础上下文压缩、第八步建立基础 Session 机制、第九步加载项目说明并带入启动上下文、第十步完成本地存储与历史回看。

## 交互方式

客户端采用本地网页。网页负责接收输入、配置模型密钥和显示运行过程；本地 Agent 程序负责组装上下文和执行工具，其中的模型服务负责向模型发送请求。密钥由本地程序保存与使用；网页仅在配置时短暂持有用户新输入的密钥，保存后不保留、不写入浏览器持久化存储。后端不向网页返回已保存的密钥，日志、状态查询和聊天响应也不包含密钥。

模型服务默认使用 `deepseek-flash`，通过 OpenAI SDK 的 Chat Completions 接口向 DeepSeek 提供的模型发送请求。模型标识和 SDK 调用方式参考 [DeepSeek 官方接入说明](https://api-docs.deepseek.com/)。

模型到后端采用 SSE 流式返回，由 OpenAI SDK 解析；后端到网页采用 WebSocket，连接、订阅和后台任务的生命周期参考本地 dsh 源码。本期直接打通：网页发送消息 → HTTP 确认接收 → 后端调用模型并接收 SSE 流式回复 → 本地服务通过 WebSocket 推送回复片段和运行状态 → 网页逐段追加到同一条回复中。模型模块与传输通道可以分层测试，交付以真实网页聊天链路为准。模型流式响应机制参考 [OpenAI Docs](https://developers.openai.com/api/docs/guides/streaming-responses)。

首版仅供本机使用；未指定的界面框架与运行环境在实现前讨论。

参考 [Pi 的运行事件设计](</Users/stardust/agent learning/pi/packages/agent/README.md#event-flow>)，将 Agent 运行与界面展示分开。相比原先的终端方案，本方案增加网页与本地程序之间的通信，核心循环仍按原有目标逐步构建。

## 范围

| 职责 | 本里程碑需要做到 |
| --- | --- |
| 上下文组装 | 整理任务说明、用户输入、历史消息和工具说明，形成每轮模型请求 |
| 模型调用 | 默认通过 OpenAI SDK 请求 `deepseek-flash`，取得流式文字回复或完整的工具调用请求 |
| 工具定义与调用接收 | 参考 Pi，本期仅统一定义 `read`、`bash`、`edit`、`write` 四种工具，从后端 Model 函数接口接入和验收，默认提供四种声明并收齐调用供后续消费；其他工具暂不纳入 |
| 工具执行 | 校验名称和参数，在绑定工作区执行六种本地工具，并通过已配置的服务商搜索网页或获取正文 |
| 控制循环 | 将模型的工具调用及对应结果加入历史，再次调用模型；管理继续和停止条件 |
| 上下文压缩 | 在同一会话中通过 `/compact` 或接近上下文上限时自动生成摘要，缩短后续模型输入；至少连续完成两次，并验证 token 下降及任务信息保留 |
| Session 机制 | 新建、列出、切换并继续不同会话；按会话区分消息、模型输入、压缩摘要、token 统计和任务状态，互不串用 |
| 项目说明加载 | 会话开始工作时，从所属项目的文件中获取基础信息，纳入模型上下文，让 Agent 据此开展工作，无须用户逐次重复说明 |
| 本地存储 | 按会话保存消息、工具调用、执行结果、运行状态及压缩记录，重启后仍可读取 |
| 网页交互 | 提供任务输入、发送、运行状态、结果显示和停止操作；通过 WebSocket 逐段展示回复，并展示工具名称、参数、执行结果及最终回答；支持查看历史会话 |

先用简单函数打通这些职责，按需要再调整结构。工具调用可以使用模型原生能力，无须额外解析文本形式的 Thought/Action/Observation。网页先用简单的聊天界面，以文字展示运行记录和回复；通过 WebSocket 逐段显示真实回复是第二步的完成条件。

- 当前对话的用户消息、模型回复和运行状态由后端内存统一持有；网页持有输入草稿和展示状态。后端从当前对话准备模型输入，同一后端下的多个浏览器页面共享当前对话。
- 运行协调统一归 Agent：保存当前对话与运行状态、接受提交、准备模型历史、调用 Model、消费模型事件并提供内部快照与更新订阅。WebServer 负责 HTTP / WebSocket 接入与网络封装，不维护第二套历史或运行状态；不再另设 Conversation 执行模块。本期 Agent 只协调单次模型调用，工具与循环仍按后续步骤推进。用户于 2026-11-01 确认这一职责归属；`ConversationMessage` 等名称只描述 Agent 持有的对话数据。
- WebSocket 建联后，网页自动发送独立的“订阅当前对话”请求；后端建立订阅，先返回当前内容与生成状态，再持续推送后续增量。本期仅实现当前对话这一种订阅。一次模型调用的 `done` 或 `error` 不结束订阅；断线时释放订阅但不取消后台生成，重连后重新订阅并从仍运行的后端恢复当前内容。关闭网页不自动取消生成。后端重启后内存聊天清空，已保存的凭据文件仍保留；聊天磁盘持久化按第十步推进。
- WebSocket 回复载荷采用 B：首次订阅或重连时发送当前对话快照与运行状态；生成中发送带正式消息 ID、内容块位置及相应块必要信息的开始、增量和块结束事件，不随每个片段重复发送整条 `partial`。`done` / `error` 携带最终完整的 `AssistantMessage`，网页据此校准当前消息；失败时仍保留已生成部分。前端负责按消息 ID 与内容块位置组装增量，Model 内部的“增量 + 当前完整回复”契约保留。
- 快照与增量按同一进度衔接：Agent 按已处理的模型事件独立更新当前状态，最终用完整回复校准，不将 Model 共享且可能领先于消费进度的 `partial` 引用直接作为可恢复对话。对话更新带连续递增序号，快照携带对应进度的序号；先登记内部订阅，再取得快照及序号，先提供快照，随后只提供未包含的更新，由 WebServer 依次封装发送。网页从本次快照建立序号基线，按顺序应用后续更新，已包含的序号不重复应用；发现跳号则暂停发送并重新订阅取得当前快照，后台生成继续。当前唯一对话使用一个更新序号，作用仅为同步展示，不改变“不做提交去重”的决定。
- 前端在 WebSocket 未连接、断线或正在恢复快照时暂停发送，仍可编辑草稿；连接恢复、收到当前对话快照且确认没有正在生成的回答后，才恢复发送。即使 HTTP 仍可用，网页也等待订阅恢复。自动重连只恢复通道与订阅，不自动重发用户消息或重新调用模型，后台已有生成继续执行。
- 本期生成期间可以继续编辑草稿，发送按钮暂不可用；后端也拒绝并发提交，当前生成完成或失败且订阅就绪后恢复发送。这是为先跑通主线而接受的简化；用户期望后续改为允许继续发送、由后端依次处理，见[消息排队待办](../../docs/设计妥协记录.md#4-生成期间暂不支持排队发送)。相同内容在后续正常发送时仍作为新调用，不做去重。
- HTTP 接收契约：先校验内容、支持的模型与当前空闲状态，明确拒绝时不写入用户消息、不调用模型；通过后生成正式用户消息 ID，将用户消息和“正在生成”状态作为同一次接收操作写入当前对话，取得对应更新序号，再返回 HTTP `202`。回执包含 `clientMessageId`、`userMessageId`、`acceptedSeq`，用于气泡对应及核对订阅是否已追到接收进度，不覆盖更新的生成状态；HTTP 不等待模型首片段或 WebSocket 送达。后台 Model 读取凭据并执行调用，失败按 `error` 与最终失败回复处理，保留已接收的用户消息并结束忙碌状态。“已接收”不保证模型调用成功。
- 提交异常区分明确拒绝与未确认：有效 HTTP 回执或订阅中出现相同 `clientMessageId` 的正式用户消息，均可证明已接收，迟到的 HTTP 错误不使结果降级。明确拒绝时，临时气泡标记“发送失败”并展示原因；网络错误或等待 10 秒仍无回执、也无接收证据时，标记“未确认接收”，通过既有订阅重新取得当前快照核对。找到正式消息后恢复正常展示，暂未找到不等于证明后端没有接收。订阅就绪且无生成后可人工发送新消息，原请求稍后出现时仍按对应编号衔接，不自动重发。失败或未确认气泡仅留当前网页内存，不进入后端历史或模型输入，刷新只恢复后端实际接收的内容；不恢复输入框，不影响新草稿。10 秒仅是 HTTP 回执等待上限，独立于模型 5 分钟数据空闲超时，不停止已接收的后台生成。
- 发送采用 B：有效发送一经在前端发起，立即清空输入框和该次草稿的撤销记录，并显示待发送消息；HTTP 接收确认在后台等待，用户可以继续编辑下一条草稿，但在本次提交确认与模型生成期间均不能再次发送。提交失败显示明确错误，不自动恢复原内容到输入框，也不自动重新提交；用户后来编辑的新草稿不受影响。该规则替代原基础页面“接收成功后才清空”的时机，取消失败恢复是用户为简化本期而接受的限制，见[相关记录](../../docs/设计妥协记录.md#5-提交失败后不自动恢复已清空的草稿)。
- 前端每次发送生成临时展示编号并随 HTTP 请求提交；后端每次正常接收都生成正式消息 ID，在 HTTP 回执和 WebSocket 消息中带回临时编号。前端据此将临时气泡替换为正式消息，后续按正式 ID 更新，兼容 HTTP 回执与 WebSocket 消息的不同到达顺序。临时编号仅用于界面对应，不按它合并、拒绝或复用正常提交；正式消息 ID 由后端独立生成。
- 对话记录编号与 Model 消息内容分开：外层 `ConversationMessage` 保存后端正式 `id`、可选的前端临时对应编号 `clientMessageId`，内层 `message` 保存 `ModelMessage`。后端管理外层编号，网页据此更新气泡；调用 Model 时提取内层消息，并沿用失败回复筛选规则。工具调用的 `ToolCall.id` 和工具结果的 `toolCallId` 仍保留在模型内容中，用于关联工具调用与结果，区别于网页消息编号。本期对话记录保存在后端内存中。
- 启动采用“日常一个服务，开发保留 Vite”：日常由一个 Node.js 后端进程在同一个本机地址提供构建后的网页、HTTP 接口和 WebSocket，网页修改后需要重新构建；开发时保留 Vite 页面服务及自动更新，由 Vite 将业务 HTTP 和 WebSocket 请求转发给同一个 Node.js 后端。具体启动命令在模块设计中确定。
- 本地访问采用 dsh 式授权：本期服务只监听 `127.0.0.1`，校验请求目标地址和浏览器来源；启动时提供带随机访问令牌的本地链接，该令牌与 DeepSeek API Key 分开。首次打开有效启动链接时，后端自动换发浏览器授权 Cookie，并跳转到不带令牌的页面；业务 HTTP 与 WebSocket 建联验证有效访问凭据。独立客户端同样先取得访问凭据再调用接口。
- 授权生命周期沿用 dsh：启动令牌只在当前后端进程中保留；Cookie 使用持久签名密钥，签发后固定 30 天有效，普通访问不自动续期，同一地址下后端重启后仍可校验。Cookie 使用 `HttpOnly`、`SameSite=Strict`，签名绑定访问地址与端口；HTTP 请求和 WebSocket 握手分别校验，不增加“Cookie 到期主动关闭已建立 WebSocket”的计时机制。模型调用仍独立于网页连接。签名密钥存于 `~/.agent-learning/browser-auth.json`，与 Pi 形式的模型凭据文件分开，以满足“模型凭据损坏时仍能访问设置”的已确认要求；文件缺失时安全创建，存在但损坏时明确报启动授权错误，不静默重置。
- 工程默认沿用 dsh，已有用户决策与 Pi 式 Model 契约优先；由这些约束推导的工程细节直接细化，不再逐项询问。需要偏离 dsh 且带来新的行为、边界或代价时，说明原因与影响后讨论。来源：用户本轮明确授权。

- [ ] **后续待办（不计入本期验收）：** 支持用户自由选择所用模型支持的推理强度，并将选择应用到模型请求。本期仍固定 `high`；具体交互、作用范围与保存方式在开展该能力时设计。来源：用户于 2026-10-30 明确要求记录。
- Model 输入采用 Pi 式 `ModelContext`：可选的 `systemPrompt`、调用方准备好的完整 `messages` 数组、可选的 `tools` 声明数组。消息类型包含 `SystemMessage`、`UserMessage`、`AssistantMessage`、`ToolResultMessage`；工具结果通过 `toolCallId` 对应原工具调用。工具声明包含名称、用途和参数规则，不携带实际执行函数。Model 负责将内部输入转换为 SDK 格式，不修改或累积传入的历史；本期纳入工具声明与工具结果输入契约，普通聊天可不传 `tools`，具体工具注册和执行仍按后续步骤推进。
- 工具参数设计属于第三步工具设计（原第四步，区别于本次聊天的第三子阶段）：具体声明与 TypeBox 选择见 Feature3，依赖版本在该步实施时验证，不因工具选型提前升级 TypeScript。`ModelContext` 中工具说明由调用方提供的职责方向保留，参数类型的具体契约届时确定；本阶段普通聊天请求不携带工具声明。已确认的 `toolCall` 内容块、结构化参数值、JSON 解析错误标记及工具块流式事件保留，区别于后续按具体工具参数定义做执行前校验。Feature3 的 TypeBox 选择不扩大本聊天阶段的普通请求范围，具体版本仍待实施验证。
- Model 的 `stream(model, context, { signal? })` 立即返回可异步迭代的 `ModelEventStream`，后台开始读取当前凭据和请求模型；Agent 持续读取事件、更新当前回复并发布内部状态变化，WebServer 再通过 WebSocket 分发给网页。流同时提供 `result(): Promise<AssistantMessage>`，等待同一次调用的最终回复，不发起第二次模型请求；凭据、网络、超时等调用失败通过 `error` 事件及最终失败回复表达，保留已生成内容。Agent 可用 `signal` 显式取消，与网页连接生命周期分开。该方式需要维护事件队列和最终结果的等待机制。
- 模型回复采用 Pi 式有序内容块：`AssistantMessage.content` 由 `text`、`thinking`、`toolCall` 三种块组成，本期直接纳入工具调用块的完整核心结构，不先做纯文本回复或推迟工具块类型。`toolCall` 表达模型提出的工具调用请求，包含调用 ID、工具名称和结构化参数；工具实际执行属于后续执行职责，不归 Model。项目内部结构由 Model 转换为 SDK 要求的请求格式。
- 模型回复除内容外保留来源、状态、用量和时间：`AssistantMessage` 包含 `role`、`content`、`api`、`provider`、`model`、可选的 `responseId` / `responseModel`、`stopReason`、可选的 `errorMessage` / `usage`、`timestamp` 和可选的 `durationMs`，由 Model 组装并更新。`stopReason` 的 `pending` 仅表示生成中，终止仍为已确认的五种结果。记录调用开始时间与总耗时；`usage` 保存服务商实际报告的输入、输出和总 token 数，未返回的用量保持未知，不填成 `0`。本期该用量结构采用上述三项计数，区别于 Pi 的缓存拆分与费用计算范围；页面如何呈现这些信息在页面模块另行确认。
- 模型流式事件采用 Pi 式完整分组：整体 `start`；正文的 `text_start` / `text_delta` / `text_end`，推理的 `thinking_start` / `thinking_delta` / `thinking_end`，工具调用的 `toolcall_start` / `toolcall_delta` / `toolcall_end`；最后以 `done` 或 `error` 结束，结束结果沿用下述五种原因。内容块事件用 `contentIndex` 定位在本条回复中的块；`toolcall_end` 只表示工具调用请求内容收齐，不表示工具已经执行，实际执行仍归后续执行职责。本期维护三类块各自的开始、增量拼接和完成状态。
- Model 内部事件采用 Pi 式“增量 + 当前完整回复”：开始与内容块事件携带 `partial`，增量事件同时提供本次片段，块结束事件提供收齐的块内容，`done` / `error` 携带本次最终回复（失败时保留已生成部分）。Model 负责组装本次回复，Agent 负责持有整段对话并取得当前回复；`partial` 是共享且持续更新的对象，不是各事件发生时的历史快照，消费方需要保留某一时刻状态时自行复制。该约定针对后端内部 Model 接口，WebServer 按前述快照、增量和最终回复方式转换为网络消息，具体字段见技术设计。
- 工具参数错误采用 Pi 的块级处理：完整参数最终无法解析为 JSON 对象时，保留 `toolCall`，将 `arguments` 设为 `{}`，以 `argumentsError` 记录错误原因与原始参数；`toolcall_end` 表示该调用请求内容收齐，不保证参数有效。模型流正常消费结束且有有效结束原因时，仍按实际原因发出 `done`，不因这类参数错误单独将整条回复标为 `error`。空参数或仅空白按 `{}` 接收；非空参数严格解析为非 null、非数组的 JSON 对象，不修复非法转义或控制字符，也不补全截断结构。见 [Feature2 Model 参数解析边界](../../docs/里程碑1/feature2/feature2-单会话流式聊天技术设计.md#key-model-stream)；该规则替代早期有限修复选择，已在 Feature2 阶段三实现。后续工具执行方必须检查 `argumentsError`、拒绝执行并反馈工具错误；本期不执行工具。
- 本地模型发现由 Model 内部的 DeepSeek 适配逻辑提供 `discoverModels()`，通过凭据模块查询已校验的配置状态，结合程序支持的本地模型目录返回可选模型。本期发现模型不向 DeepSeek 发起模型列表或密钥验证请求；`auth.json` 保存提供方凭据，不保存模型目录，前端只取得模型信息与非敏感凭据状态。
- 初始化触发本地模型发现；用户在网页新增、更换或删除凭据时，先由凭据模块校验并安全更新文件，成功后重新计算可选模型列表并更新前端。实际发起模型调用时，Model 再通过凭据模块取得当前 Key，校验后交给 OpenAI SDK 组装认证与请求，向 DeepSeek 发起调用；Model 不直接读取 JSON。后端调用方仍负责准备历史消息，本地凭据检查通过不等于远端调用已验证成功。
- 模型流的结束事件采用 Pi 的区分方式：`done` 事件的 `reason` 为 `stop`（正常回答结束）、`length`（达到输出长度上限）或 `toolUse`（模型要求调用工具）；`error` 事件的 `reason` 为 `error`（调用失败，包含超时）或 `aborted`（调用被取消）。以两类事件覆盖这五种结束结果，本期内容块契约同时纳入 `toolCall`，具体工具定义、执行与结果回传仍按后续工具步骤推进；一次模型调用结束不等于后续 Agent 整个任务完成。模型调用不自动重试，显式关闭 SDK 的自动重试；一次请求失败就返回 `error`，临时故障由调用方重新发起。
- 正常结束要求收到模型有效的结束原因且 SDK 流正常消费结束；请求、模型传输或协议解析、超时失败，以及缺少有效结束原因的提前断流，都返回 `error`。模型生成的工具参数内容错误按上述 `argumentsError` 契约处理，与模型流错误区分。一次正常完整消费的调用只产生一个终止事件，终止之后不再产生片段；首次文字之前失败也返回 `error`。本期完整纳入正文、推理和工具调用的模型回复结构；具体工具定义和执行分别按第三、第四步推进。
- 模型请求采用 5 分钟空闲超时：从发起请求开始等待，连续 5 分钟没有收到 SDK 返回的模型数据则中止请求，返回明确的超时 `error`，完成收尾并恢复发送，不自动重试；收到正文、推理等模型数据后重新计时，持续返回数据时整次回答可以超过 5 分钟。该规则覆盖首次数据等待和后续流式读取；只收到原始 SSE 心跳、没有 SDK 返回的模型数据仍算空闲。
- 后端已接收的调用在模型生成失败或超时后，保留用户消息与已生成的回复内容，回复明确标记失败或超时，刷新或重连后仍可从运行中的后端恢复展示。下一次模型请求保留用户消息，排除这条失败的模型回复；筛选由后端准备消息时完成，Model 不管理历史。用户随后只说“继续”时，模型看不到被排除的回复前缀，不能保证接着该前缀回答。
- 不做提交去重：用户再次发送相同内容，按新的一次正常提交与模型调用处理，不按文本或提交编号合并、复用先前调用。消息编号仅用于标识和更新对应消息，不作为去重依据。
- [x] 凭据文件按 Pi 的 JSON 形式组织，保存到本机应用用户数据目录下、本项目自己的 `auth.json`；读写和更新机制参考 dsh。本期只提供网页设置这一配置入口：网页通过 HTTP 将用户新输入的密钥交给后端，由后端凭据模块保存、更换、删除和查询非敏感配置状态，不增加独立本地配置命令。模型调用只从本项目的 `auth.json` 读取密钥，不使用环境变量回退；删除保存的密钥后即无可用密钥，后续请求使用更新后的配置。该文件不与 Pi 或其他程序共用。

### 第七步：基础上下文压缩

[验收标准](./feature7/feature7-验收标准.md)与[实施计划](./feature7/feature7-实施计划.md)。

目标：让同一个当前会话在内容变长后，能够把较早的内容整理成摘要，减少下一次交给模型的 token，同时保留继续原任务所需的信息。

- [x] **真实摘要压缩：** 以 [Pi 的压缩设计](</Users/stardust/agent learning/pi/packages/coding-agent/docs/compaction.md>)及[实现源码](</Users/stardust/agent learning/pi/packages/coding-agent/src/core/compaction/compaction.ts>)为主要参考，由真实模型整理较早的消息，后续请求使用“摘要 + 保留的近期消息”，不再重复携带已被摘要替代的原文。不能仅删除消息、截断文字或在页面显示一段摘要来冒充压缩。
- [x] **主动触发：** 用户在聊天输入框提交 `/compact`，由本地程序识别为压缩命令并触发压缩，不作为普通聊天内容交给模型回答。网页明确显示正在压缩、成功或失败。
- [x] **自动触发：** 根据下一次模型请求预计占用的 token 与所用模型的上下文上限判断，在接近上限时自动压缩，为摘要生成和后续回复预留空间，不以消息条数作为唯一条件，也不只等到服务商报超限才处理。检查覆盖新用户输入及循环中新增的工具结果；阈值、预留量与估算方法在技术设计中确认。
- [x] **同一会话反复压缩：** 至少能在不清空、不重建会话的情况下，先后完成两次完整压缩；两次是最低验收次数，不是功能次数上限。第二次整理上次摘要与此后新增且需要压缩的内容，形成更新后的摘要，保留早期仍有效的信息并纳入后续更正，不简单堆叠旧摘要。近期保留消息中的工具调用和对应结果不能被拆散，压缩与模型生成、工具执行的衔接遵守第五、六步的停止规则。
- [x] **token 可核对：** 网页分别展示每次压缩的触发方式、压缩前后上下文 token、减少量及统计依据。估算值必须标明“估算”，未知值不填成零；在压缩后的真实后续请求中，用服务商实际报告的输入 token 复核下降。比较的是后续请求的完整输入，不是页面字数、输出 token、缓存折扣或累计消耗；生成摘要本身的用量另记，不混入前后对比。
- [x] **信息保留：** 摘要保留任务目标、用户约束、关键事实、已经确认及后来更正的决定、已完成与未完成的工作、继续任务所需的文件路径和工具结论。用后续真实问答与继续执行原任务检验，不只根据摘要看起来完整或模型自评判断质量；不承诺逐字保留或任何任务都绝不遗失信息。
- [x] **失败保护与记录：** 摘要生成失败、取消或没有有效缩短上下文时，不能报告压缩成功或替换原有效上下文；仍超限时明确停止并说明原因，不无限压缩或重试。压缩只改变后续模型输入，原始聊天与工具记录仍留在后端内存供网页查看，刷新或重连能恢复压缩进度和结果；本步不要求重启恢复，磁盘保存留到第十步。
- 验收：在同一个真实网页会话中先通过 `/compact` 完成第一次压缩，继续聊天和工具操作，再达到明确的 token 阈值自动完成第二次；两次均能核对真实输入 token 下降，并在每次之后通过关键事实问答和任务续做验证信息保留。第二次特别验证仅存在于第一次摘要中的早期事实，以及第一次之后新增或更正的信息。完整案例见下方“上下文压缩（第七步）”。

与 Pi 的取舍：沿用摘要、近期消息和重复压缩的主流程；本步不引入分支摘要、会话树或扩展钩子。Pi 的压缩后 token 展示包含估算，本项目按用户标准补充真实后续请求用量复核。阈值、切分边界、摘要格式、命令与事件契约、超长单条消息或工具结果的处理，以及溢出后的恢复策略，在第七步技术设计时说明风险并确认，不在此提前锁定实现。

### 第八步：基础 Session 机制

目标：Session 就是一段有独立编号的会话。用户可以在任务运行时自由新建或切换会话，也可以让不同会话同时执行任务。A 的历史、任务和压缩摘要各自留在 A，切回后可以继续查看和操作。[技术设计](./feature8/feature8-基础Session机制技术设计.md)已实现，分支上的首发验证见[复跑记录](./feature8/feature8-验收标准.md#first-send-results)。

- [x] **新建与切换：** 正式会话各有独立且稳定的编号。侧栏顶部与工作区的新建入口共用一份未发送草稿，可在输入框上方选择目录。首条消息被接收后，才在最终选中的工作区登记会话。切换时保留已有会话，切回后可以继续聊天和工具操作。
- [x] **上下文隔离：** 每个 Session 独立持有用户消息、模型回复、工具调用与结果、有效模型上下文、第七步的压缩摘要与边界、token 统计。准备模型请求时，只使用目标会话的数据和适用的公共配置；A 的历史或摘要不会自动进入 B。
- [x] **运行与消息归属：** 提交、订阅、流式更新、工具结果、压缩和中止都明确归属目标 Session，后端校验会话编号；不存在的会话明确报错，不默默回退到另一个会话。切换、迟到的响应、刷新或重连不能把 A 的内容显示或写入 B，也不能把原本针对 A 的中止作用到 B。
- [x] **会话并行：** A 执行任务时可以新建或切到 B，也可以在 B 启动任务。A 在后台继续，切回后能查看其进度或中止当前任务。同一会话仍一次执行一个任务。
- [x] **多个工作区：** 用户可选择多个已有的本机文件夹，分别添加为工作区。侧栏按工作区组织会话，每个工作区可新建多个 Session。后端按目标 Session 的工作区执行工具，切换到别的工作区或会话时，已有任务仍在原目录执行。客户端参考 DSH，后端目录归属参考 Hermes。
- [x] **基础生命周期：** 同一后端进程内保留各会话的内容和状态，刷新或重连后能重新选择并继续已有会话；打开新会话草稿、切换目录或切换会话本身不触发模型请求或工具执行。本步不要求后端重启后恢复，落盘与历史读取留到第十步。
- [x] **草稿恢复：** 两个新会话入口共用首发草稿，首条消息被接收后清空。已开始会话的草稿按会话保存在同一浏览器，切换、刷新或重新开页后，只要原会话仍可打开，就能继续编辑原草稿。
- 验收：在同一工作区新建 A、B 两个会话，分别进行真实聊天和工具操作，来回切换后各自接续；检查页面、实际模型输入、工具结果、压缩记录和运行状态均按会话归属隔离。补测刷新、重连、迟到响应、中止及无效会话编号，具体操作与检查结果见[功能 8 验收标准](./feature8/feature8-验收标准.md)。

**已确认的写入与失败规则**

- 纯文字回复先保留已经生成的内容，首次写入失败时在本轮收尾再尝试保存。收尾后仍未保存时，在本轮末尾显示红点和「回答已生成，但未保存」。
- 模型回复包含工具调用时，先保存调用记录。写入失败时结束本轮，本批工具未执行。
- 串行工具逐项执行、保存结果并通知完成。某项结果写入失败时结束本轮，保留已保存的结果和已发生的文件改动，后续工具未启动。
- 并行工具整批收尾后，按模型提出调用的顺序逐条写入结果，沿用 [Pi](../../pi/packages/agent/src/agent-loop.ts#L646) 和 [Hermes](../../hermes/agent/tool_executor.py#L1607) 的落盘时机。完成通知按 Hermes 的做法在对应结果写入成功后发布。某项结果写入失败时结束本轮，后续结果停止写入和发布完成通知。
- 工具执行成功且结果写入成功后，网页才显示该工具成功。工具已经执行、结果写入失败时，该工具卡片状态为 `Error`，只显示「工具已执行，结果未保存」，详情入口关闭。本轮末尾显示保存失败。
- 写入失败的提示属于后端会话状态。同一个服务进程内，刷新网页、重连或重新打开会话时，页面重新取得这条提示。
- 服务中断后，若已保存的记录只有工具调用且无法确认执行结果，工具显示「结果未知」。用户主动发送下一条消息时，模型会收到上一轮中断、工具结果未记录的说明。对于可能改变文件等外部状态的操作，提醒模型先核对现状，再决定是否执行。

### 单轮工具调用（第四步）

在临时工作区准备 `note.txt`，内容为「项目名称：青禾」。从网页让 Agent 用相对路径读取，核对实际工具调用、读取结果、模型收到的回填以及最终回答。将文件中的项目名称换成「白榆」后重测。其余七种工具的独立场景见 [Feature4 验收设计](../../docs/里程碑1/feature4/feature4-工作区选择与四工具执行.md#6-验收标准)。

### 多轮工具调用（第六步）

再准备 `index.txt`，内容为 `项目信息见 note.txt`。在网页输入：

> 读取 index.txt，按照其中的线索找到项目名称。

验收：模型先读取 `index.txt`，收到结果后再请求读取 `note.txt`，最后回答“青禾”。记录中应有至少两轮先后发生的工具调用，每次结果都进入下一轮上下文；不将一次回复中同时提出的多个工具请求算作多轮决策。

### 上下文压缩（第七步）

从一个新的当前会话开始，本案例中的两次压缩及后续验证始终使用这个会话，不在两次之间清空历史、重启后端或新建会话。

1. 准备包含用户目标、关键事实、明确约束、已确认决定、工具结论和未完成工作的对话，并预先列出应保留的信息与任务完成条件。后续用于核对的早期信息必须进入待压缩部分，不能全部藏在保留的近期原文中。
2. 让历史增长到足以压缩后，在网页提交 `/compact`，调用真实模型生成摘要。核对后续请求实际使用摘要与保留消息、已替代原文没有重新混入输入；网页可见第一次压缩的过程及 token 变化。
3. 第一次压缩后，通过真实问答核对早期事实和约束，并继续原任务；随后加入新事实、对原决定的更正以及新的工具结果。让下一次请求达到已说明的 token 阈值，确认无需输入 `/compact` 即自动完成第二次压缩。可在受控验收环境降低触发阈值来缩短准备过程，但必须标明实际模型上限与测试阈值，不能伪造 token 用量或压缩结果。
4. 第二次压缩后继续真实问答和原任务，核对第一次摘要中的早期信息仍在、后来更正的决定已经更新、新工具结论与未完成工作没有丢失。其中至少一项早期事实在第一次压缩后的问答中没有再次出现，确保第二次必须依赖摘要而不是近期问答原文。核对时不能重新把被压缩原文、标准答案或完整历史塞回模型；通过新工具操作继续完成任务，并检查实际结果。
5. 两次各自保存压缩前后可比的输入 token 证据：使用相同模型、相同系统提示和工具声明，并以相同验证输入作对照，采用服务商报告的真实输入用量确认下降；生成摘要本身的调用另记。页面即时估算与后续真实用量分开标示，缺失真实用量时明确记为尚未完成此项验收，不用假数据代替。
6. 补充失败、取消、摘要未缩短和工具调用关联检查：原有效上下文不因失败丢失，不把失败记成成功，不出现无限自动压缩，也不产生孤立的工具结果。

真实验收记录应包含两次触发方式、摘要及保留范围、token 对比依据、预先列出的关键信息逐项核对结果和继续任务的实际结果。通过本案例表示基础场景的信息保留达标，不表示任意长会话都能无损压缩。

### Session 机制（第八步）

本案例从空的测试会话集合开始，在同一工作区中建立两个不同的 Session，不通过重启或清空 A 来制造 B。

1. 从侧栏顶部打开新会话草稿，输入一组测试专用的随机代号和约束，再从工作区的新建入口打开，确认仍是同一份草稿。首发被接收后，核对只在最终选中的工作区登记 A，并进行真实聊天与工具操作。再用另一组代号和约束首发建立 B，确认它没有 A 的聊天记录。
2. 在 A、B 中分别询问本会话的代号、约束和任务进度，再来回切换继续对话。回答应各自接续；同时核对后端准备的实际模型输入只包含目标会话的历史，不能只凭模型回答“我不知道”就认定隔离成立。测试信息不预先写入共用文件或公共提示词。
3. 在 A 中按第七步条件完成压缩，确认 B 的历史、有效上下文、摘要、压缩次数和 token 统计没有因此变化；B 的后续模型请求不携带 A 的摘要，A 仍可从自己的摘要继续任务。
4. 让 A 保持运行，切到 B 并发送消息，核对两个任务的运行时间确实重叠。来回切换，检查流式更新、迟到回执和工具结果各自归属。切回 A 中止，核对 B 继续运行，A 已取得的结果仍可查看。
5. 刷新网页或断线重连，再分别打开 A、B，确认内容和状态各归其主。
6. 在 A、B 写入不同的未发送草稿。切换、刷新，以及关闭标签页并在同一浏览器新开页面后，分别打开 A、B，核对草稿原文、空格和换行各自保留。
7. 提交不存在的 Session 编号时明确拒绝，A、B 的内容不变。打开新会话草稿、选目录和切换会话本身不产生额外的模型调用或工具执行。
8. 添加两个目录作为工作区，在两个目录分别放置内容不同的 `note.txt`。从各自工作区的会话要求读取相对路径 `note.txt`，核对实际工具目录和返回内容分别来自所属工作区。运行中切换页面后，先前任务继续使用原目录。

记录真实请求所用的 Session、各自上下文和工具结果归属、两项任务确实同时运行的证据，以及网页切换后的内容。工作区文件由各会话共享，服务重启恢复由第十步验收。

### 项目说明加载与启动上下文（第九步）

在项目文件中预先提供可核对的项目背景和工作约定，启动属于该项目的 Session；用户只提出任务，不重新介绍这些资料。检查真实模型输入及后续回答或执行结果，确认 Agent 已取得并使用项目信息。再核对会话切换后的资料归属，与已有聊天、压缩和 Session 隔离能力共同工作。具体文件约定和验收操作在本步设计时确定。

### 本地存储与历史回看（第十步）

本案例另从新的测试会话集合开始，建立 A、B 两个 Session，在 A 内完成至少两轮工具调用及两次压缩，在 B 内保留不同的聊天与工具记录。再刷新网页并重启本地服务，从历史会话列表分别打开 A、B。确认各自的原始消息、工具调用、对应结果、压缩记录和最终回答都能按原编号和顺序显示，不互相覆盖或混入另一会话，且查看过程不产生新的模型请求或工具执行。再验证任务中断和保存失败时的提示与已有记录保护。

重启后在 A 主动发送一条依赖此前对话的新消息，核对实际模型输入沿用 A 已保存的压缩摘要与近期原文。另在任务运行中重启，核对旧任务显示「已中断」，用户发送消息后才开始新一轮。

用真实模型跑通模型 SSE 与网页 WebSocket 的流式链路、单轮和多轮工具调用、同会话两次压缩、Session 创建切换与隔离、项目说明加载与实际使用案例，并用简单测试或断言检查文本片段拼接、完成与错误状态、工具结果回填、工具失败、超时、用户停止、重复压缩、token 统计依据、压缩失败保护、会话归属、存储读写一致性和重启后历史回看；不只根据最终回答判断闭环是否成立。

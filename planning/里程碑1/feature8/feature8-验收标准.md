# Feature 8 基础 Session 机制验收标准

共 **41 个案例，分为 7 个主题**。验收目标是确认用户可以添加多个已有目录，自由新建、切换和找回会话，并能在不同会话中同时执行任务。每段会话使用自己的工作区、聊天、工具结果、压缩记录和运行状态。通用 Agent 也需能独立运行并向调用方交付结果。案例中的目录、文件、文本和编号为构造示例。验收入口和复跑结果见[执行说明](#execution)。下列案例保留当时的交互。单一草稿与首发创建覆盖原来提前创建空会话的步骤，见[新会话首发复跑](#first-send-results)。

## 1. 工作区添加与保留

<a id="case-01"></a>

### 01 从旧登记添加第二个工作区后原工作区编号不变

- **类型** 集成测试（临时登记文件与目录）。
- **目的** 验证旧版工作区数据可以直接用于多工作区。
- **怎么测** 准备含 `boundWorkspaceId` 的旧版登记文件，已有「青禾」，编号为 `workspace-qinghe`。通过工作区添加接口选择已有目录「白榆」。核对列表和写回的登记文件包含两个不同的编号及各自路径，「青禾」仍用原编号。

<a id="case-02"></a>

### 02 服务重启后仍能读到两个已登记工作区

- **类型** 集成测试（临时登记文件与目录）。
- **目的** 验证多工作区登记跨服务重启保留。
- **怎么测** 记录已登记的「青禾」和「白榆」的编号与路径。关闭服务，用同一登记文件启动，再查询工作区列表。核对两项都保留原编号和路径，目录均可用。

<a id="case-03"></a>

### 03 通过符号链接重复选择目录时复用原工作区

- **类型** 集成测试（真实符号链接）。
- **目的** 验证同一个实际目录只登记一次。
- **怎么测** 已登记「青禾」后，通过添加接口选择指向它的符号链接。核对回执为 `workspace-qinghe` 和 `created: false`，列表仍只有一条。

<a id="case-04"></a>

### 04 取消目录选择后保留已有登记和当前会话

- **类型** 组件测试（注入取消结果）和集成测试（使用受控目录选择器）。
- **目的** 验证取消添加不会影响已有工作。
- **怎么测** 在「青禾」的 A 会话打开添加面板，让选择器返回取消。核对服务返回 `{ cancelled: true }`，登记文件原文与会话列表不变，网页仍打开 A。

<a id="case-05"></a>

### 05 首次添加第二个工作区后自动打开该目录下的空会话

- **类型** 组件测试（Chromium）。
- **目的** 验证可以从已有工作区继续添加目录，并直接开始新会话。
- **怎么测** 侧栏已有「青禾」，点击「添加工作区」并返回首次登记的「白榆」。核对两个分组都可见，新建请求使用「白榆」的编号。交付该会话的空快照后，核对页面选中「白榆」下的会话，消息列表为空，输入区显示「白榆」目录。

<a id="case-06"></a>

### 06 工作区登记成功但建会话失败时仍可从侧栏重试

- **类型** 组件测试。
- **目的** 验证自动打开失败时保留已完成的工作区登记。
- **怎么测** 打开「青禾」的 A，添加「白榆」。让登记成功，但在新建空会话时返回目录不可用。核对「白榆」仍在侧栏，页面保留 A 并显示失败原因。目录恢复后，从「白榆」的工作区行再点新建，核对空会话出现在其分组下。

<a id="case-07"></a>

### 07 添加工作区的回执晚到时保留用户较新的会话选择

- **类型** 组件测试。
- **目的** 验证后台登记完成时不会把用户拉离刚切换的会话。
- **怎么测** 在 A 发起添加「白榆」，暂缓返回登记结果。切到已有的 B 并交付 B 的快照，再返回「白榆」登记成功。核对侧栏出现「白榆」，页面仍选中 B。

## 2. 会话新建与切换

<a id="case-08"></a>

### 08 在同一工作区新建两段会话时各有独立编号和空历史

- **类型** 集成测试。
- **目的** 验证每次新建都在指定工作区创建独立会话。
- **怎么测** 在已登记的「青禾」依次新建两段会话并分别订阅。核对两个 `201` 回执中的会话编号不同、工作区编号相同，默认名称依次为「会话 1」「会话 2」。两份快照均为空闲且没有消息，模型与工具调用次数均为零。

<a id="case-09"></a>

### 09 切回已有会话可查看原历史且不启动任务

- **类型** 组件测试。
- **目的** 验证浏览已有会话只切换显示和订阅。
- **怎么测** 让 A 已完成「读取 a.txt」，B 已完成「读取 b.txt」。在 B 点开 A，等 A 的快照到达。核对选中标记、消息及工具结果都属于 A，发送和中止请求计数没有增加。

<a id="case-10"></a>

### 10 新建会话的回执晚到时只更新列表

- **类型** 组件测试。
- **目的** 验证创建新会话和选择当前会话可以分别完成。
- **怎么测** 在 A 点击新建，暂停新会话 C 的回执。先切到已有的 B 并取得 B 的快照，再交付 C 的创建回执。核对 C 出现在所属工作区下，B 仍被选中，当前订阅仍指向 B。

<a id="case-11"></a>

### 11 新建回执丢失后能从列表找到已创建的会话

- **类型** 组件测试。
- **目的** 验证请求已创建会话但网页未收到回执时，用户仍能打开结果。
- **怎么测** 在 A 发起一次新建。模拟服务已创建 C、网页没收到回执，让重查的会话列表包含 C。核对网页没有自动再次创建，用户能从列表点开 C 并取得它的空快照。

<a id="case-12"></a>

### 12 订阅不存在的会话后仍能用原连接打开其他会话

- **类型** 集成测试（真实 WebSocket）。
- **目的** 验证无效订阅会明确失败，且不会被当成另一个会话。
- **怎么测** 服务中已有 B，连接后订阅 `session-missing`。核对错误带该会话编号和本次订阅编号。用同一连接订阅 B，核对随后收到 B 的快照。

<a id="case-13"></a>

### 13 切到 B 后忽略 A 的迟到更新

- **类型** 集成测试（网页通信与状态）。
- **目的** 验证切换会话后只应用当前订阅的数据。
- **怎么测** 从 A 切到 B，先交付 B 的快照，再送入 A 的旧订阅片段「青禾完成」。核对 B 的快照和内容未被改写。随后交付 B 的连续更新「白榆完成」，核对这段文字正常出现。

## 3. 草稿与会话恢复

<a id="case-14"></a>

### 14 来回切换时各会话保留自己的草稿原文

- **类型** 组件测试（Chromium）。
- **目的** 验证两份未发送文字各自保存。
- **怎么测** 在 A 输入两行「先跑测试」「再整理结果」，保留整段首尾各两个空格；在 B 输入「检查 README」。来回切换，核对两段原文各自恢复，空格和换行保留。

<a id="case-15"></a>

### 15 运行中刷新后找回原会话、草稿和输出

- **类型** 端到端测试（Chromium、受控模型流）。
- **目的** 验证实际网页重新加载后能同时接上浏览器存储和服务中的运行。
- **怎么测** 在 A 看到回复片段「第一段已经到达」后暂停模型流，输入带换行的未发送草稿。刷新网页，核对重新打开 A，任务编号和已输出文字相同，草稿逐字符保留，模型请求仍为一次。切到 B 时仍能看到 B 原有记录。

<a id="case-16"></a>

### 16 关闭后新开标签页仍能找回最近会话和各自草稿

- **类型** 端到端测试（同一 Chromium 浏览器上下文）。
- **目的** 验证新标签页无需原页面内存，也能恢复后端仍存在的会话和草稿。
- **怎么测** 在 A 写入首尾各两个空格的两行草稿「先跑测试」「再整理结果」，在 B 写入「检查 README」，最后打开 A。保持服务运行，关闭应用标签页，再在同一浏览器打开应用。核对页面自动回到 A，A 的原文、空格及换行完整；手动打开 B 后只看到 B 自己的草稿。

<a id="case-17"></a>

### 17 断线重连后原会话继续显示离线期间的输出

- **类型** 端到端测试（Chromium、受控模型流）。
- **目的** 验证断线只影响网页连接，后台任务及本页草稿可以接续。
- **怎么测** 在 A 运行时输入「断线期间保留的新草稿」。让浏览器断线，再让后端收到模型片段「离线时继续生成的第二段」。恢复网络后核对当前仍是 A 的同一次运行，新增回复和草稿可见，发送请求未重复；打开 B 确认没有 A 的回复。

<a id="case-18"></a>

### 18 两个标签页编辑同一会话后刷新读到最后保存的草稿

- **类型** 组件测试（Chromium，同源标签页）。
- **目的** 验证同一浏览器的标签页共享同一个会话的保存记录。
- **怎么测** 两个标签页都打开 A。先在第一个保存「第一份」，再在第二个保存「最后保存」。刷新第一个标签页，核对恢复 A 和「最后保存」。

<a id="case-19"></a>

### 19 另一标签页打开 B 后当前页仍显示 A，刷新才打开 B

- **类型** 组件测试（Chromium，同源标签页）。
- **目的** 验证各标签页当前选择独立，重新加载时读取浏览器共享的最近打开记录。
- **怎么测** 让第一个标签页打开 A，第二个标签页随后打开 B 并收到 B 的快照。核对第一个标签页仍显示 A。刷新第一个标签页，核对自动打开仍存在的 B。

<a id="case-20"></a>

### 20 浏览器存储不可用时仍可在当前页面继续编辑

- **类型** 组件测试。
- **目的** 验证存储故障不会丢掉当前页面的输入。
- **怎么测** 让浏览器本地存储读写失败。在 A 输入「本页保留」，切到 B 再切回 A。核对 A 草稿仍在，页面提示重新打开后无法恢复这份草稿。

<a id="case-21"></a>

### 21 服务重启后最近会话已失效时回到列表

- **类型** 组件测试（注入服务重启后返回的列表）。
- **目的** 验证浏览器发现会话已不存在时仍可使用已有工作区。
- **怎么测** 浏览器保存最近会话 A 和 A 的草稿，重新加载时让后端返回原工作区、空会话列表。核对网页提示 A 不可用，显示工作区及新建入口，未把 A 的草稿加载到其他会话。

## 4. 并行任务、目录与中止

<a id="case-22"></a>

### 22 向不存在的会话提交时拒绝且不影响已有会话

- **类型** 集成测试（实际 HTTP）。
- **目的** 验证消息提交只能写入明确的目标会话。
- **怎么测** 已有 A、B，向 `session-missing` 提交「读取 note.txt」。核对返回 `404`，A、B 快照保持原样，模型与工具调用次数均为零。

<a id="case-23"></a>

### 23 同一会话正在运行时拒绝第二次提交

- **类型** 集成测试（受控模型流）。
- **目的** 验证一个会话一次只接收一项任务。
- **怎么测** 让 A 的「读取 a.txt」等待模型输出，再向 A 提交「继续读」。核对第二次返回 `409`，A 只有一条已接收请求和一次模型调用。

<a id="case-24"></a>

### 24 会话编号和运行编号不匹配时不会中止任务

- **类型** 集成测试（受控模型流）。
- **目的** 验证中止必须匹配目标会话的当前运行。
- **怎么测** A、B 都在等待模型输出。用 A 的会话编号与 B 的运行编号请求中止。核对 `handled: false`，两个任务都未收到取消且仍在运行。

<a id="case-25"></a>

### 25 A 的迟到拒绝只在 A 恢复原草稿

- **类型** 组件测试。
- **目的** 验证迟到拒绝不会覆盖当前会话的草稿或按钮状态。
- **怎么测** 在 A 发送「读取 a.txt」并延迟回执。切到空闲的 B 写「读取 b.txt」，再让 A 收到明确拒绝。核对 B 草稿及发送按钮不变。切回 A，核对原文恢复且显示发送失败。

<a id="case-26"></a>

### 26 A 收到迟到拒绝时保留后来保存的新草稿

- **类型** 组件测试。
- **目的** 验证拒绝后的自动恢复不会覆盖浏览器里较新的编辑。
- **怎么测** 在 A 发送「读取 a.txt」后切走，暂缓回执。从另一个同源标签页给 A 保存「先读 README」。让原请求收到明确拒绝，再在原标签页打开 A。核对仍显示「先读 README」及失败提示。

<a id="case-27"></a>

### 27 A 的提交未确认时 B 仍可以发送

- **类型** 组件测试（受控计时）。
- **目的** 验证已有的等待确认规则只限制对应会话。

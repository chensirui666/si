| 案例 | 实际检查 |
| --- | --- |

| 26–28 | 工具完整返回后写入一次，SQLite 中保留一条匹配结果。下一步骤发出六次请求，每次输入都包含原工具结果。失败后切换模型并发送「继续」，原会话新一轮完成，输入保留工具结果并排除失败片段。在等待中强制终止服务后，历史为「已中断」，可回看工具结果，重启后请求总数仍为两次。 |

npm run build:packages
MODEL_LIVE_KEY_FILE=/absolute/path/to/test.env npm --prefix packages/server run test:models:live -- -t '模型请求恢复正常调用' --reporter verbose --silent=false

### Google 未收到终态的补充复验

已定位到客户端发送请求体后、收到 HTTP 响应头前。复现时应用已受理会话，但 Google 流还未建立。原验收在 115 秒结束，早于产品配置的 300 秒模型空闲超时，所以当时仍为 `running`，也没有可触发重试的模型错误。

| 检查 | 实测结果 |
| --- | --- |
| 正式服务入口，`gemini-3.7-flash` | 单次请求体在 311 毫秒时发出。114.978 秒时因验收结束中止。此前没有响应头、响应流或重试事件。 |
| 正式服务入口，`gemini-3.7-flash`，显式使用本机已有代理 | 单次请求体在 6.125 秒时发出。114.972 秒时因验收结束中止。此前同样没有响应头。 |
| 延长原型号的真实验收窗口 | 首次请求在 115.447 秒收到 `UND_ERR_SOCKET`，略晚于原验收的截止时间。第二次请求从调用 `fetch` 起 180.162 秒收到同类错误，两次都没有响应头。修复前会话会重试，提示为「模型请求异常」。 |
| 跳过 Agent 和 SDK，直接请求 Google REST | 查询同一型号返回 HTTP 200，用时 3.433 秒。最小流式生成请求到 50 秒仍没有响应头。普通非流式生成请求在 30 秒超时。用 curl 分别选用 HTTP/2、HTTP/1.1 请求流式接口，两次也都在 30 秒超时，HTTP 状态码均未返回。 |
| 正式服务入口，`gemini-3.8-flash` | 会话在 14 毫秒时受理，单次请求体在发起 HTTP 调用后 1.628 秒发出。65 秒时仍无响应头。调用中止接口后，客户端关闭请求，随后服务通过 WebSocket 发布 `aborted`，中止回执确认处理成功。 |

客户端证据无法再区分链路中间环节与 Google 服务端的处理。Google 流式接口契约见 [Google Gemini API 文档](https://ai.google.dev/api/generate-content?hl=en)。

模型适配层现将等待响应头时收到的明确套接字关闭信号 `UND_ERR_SOCKET` 归为「模型连接中断」，原 Run 仍使用有限重试。通过本地 HTTP 端点先接收完整请求体，再关连接且省略响应头，验证该场景在修复前为 `request-error`，修复后为 `connection-reset`，每次只发一个请求。 [模型错误归类](../../../packages/model/src/model-failure.ts) · [模型流测试](../../../packages/model/test/model-stream.test.ts)

另一项受控测试让 Gemini 持续等待响应头，验证第 299.999 秒仍在等待，第 300 秒关闭传输并产生 `timeout` 模型错误，适配器只发起一次请求。真实验收日志现在分别记录会话受理、模型流开始、首个输出、模型结束和会话终态的耗时。受控成功回复已验证上述五个时间点。

修复后用真实 `gemini-3.7-flash` 从正式服务入口复验。请求体在 298 毫秒时发出，151.707 秒时收到 `UND_ERR_SOCKET`，期间未收到响应头。原 Run 发布 `connection-reset` 和第 1/5 次有限重试状态。收到重试状态后主动中止，服务确认 `aborted`。本次验证了真实断连的归类、重试状态和中止收尾，完整回答仍待 Google 生成接口返回。

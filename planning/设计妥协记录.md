# 设计妥协记录

记录为了当前范围而接受的简化，以及后续重新评估的时机。后续设计先检查是否触发对应条件；“更好的做法”是届时讨论的方向，不是提前要求实现的新架构。

当前条目来自已确认的 Feature1 模块设计；[合并后的技术设计](./里程碑1/feature1-基本聊天页面.md)待整体批准。

## 1. 发送后的消息暂由 ChatPage 保存在页面内存

- **妥协点：** 消息依赖当前页面，没有独立会话层和持久化。
- **当时的设计：** Lexical 管理草稿，`ChatPage` 用 React 状态保存发送后的消息，列表只读展示；`App` 只装配页面。刷新或关闭页面后清空。
- **为什么这样设计：** Feature1 只验证本地页面的输入、发送和显示，当前没有服务端消息或运行状态需要协调。
- **更好的做法：** 当会话职责出现时，由独立会话层协调消息和运行状态，让界面读取所需数据；按里程碑计划增加本地磁盘保存。草稿仍由编辑器管理，具体分层届时设计。
- **解决时机：** 第三步接入 SSE 时评估消息归属与接收状态；第八步解决持久化和历史回看。如果多处界面开始重复协调同一会话，提前重新评估。
- **来源：** [Feature1 技术设计 §4.3](./里程碑1/feature1-基本聊天页面.md#43-草稿归-lexical发送后的消息归-chatpage)、[§5 风险 4](./里程碑1/feature1-基本聊天页面.md#风险-4刷新页面后消息和草稿都不见了)。

## 2. 暂用 Vite 开发服务提供页面

- **妥协点：** 当前入口依赖前端开发服务，还没有与本地 Agent 服务组成完整应用入口。
- **当时的设计：** 用现有 Node.js 和 npm 运行 Vite，浏览器打开本机开发页面。
- **为什么这样设计：** Feature1 尚无后端，不必为展示页面先建设完整本地服务。
- **更好的做法：** 本地服务形成后，评估由本地应用提供构建后的网页及业务接口，形成一致的启动方式；开发时仍可保留 Vite。
- **解决时机：** 第三步连接网页与模型服务时评估；需要让别人直接启动使用、无需理解前端开发工具时解决完整入口问题。
- **来源：** [Feature1 技术设计 §4.1](./里程碑1/feature1-基本聊天页面.md#41-使用-react--typescript--vite在-web-内组织网页代码)。

## 3. 提交和消息内容暂时只表达普通文字

- **妥协点：** 字符串不能完整表达引用目标，当前消息类型也只有用户角色。
- **当时的设计：** 输入接口为 `onSend(text: string): boolean`，消息使用 `{ id, role: 'user', text }`；普通用户文字按原文展示。
- **为什么这样设计：** Feature1 没有模型回复和引用标签产生的数据，只需提交和展示文字。虽然已经选用 Lexical，仍不提前建立引用数据结构。
- **更好的做法：** 引入对应功能时，按实际需要扩展消息角色、结构化内容和提交接口；引用标签应携带目标信息，不能只保存可见名称。异步服务的接收结果与后续运行结果也要分别设计。
- **解决时机：** 第三步加入 AI 回复时扩展消息类型与展示；开始设计引用标签时，一并调整编辑内容、提交接口和消息展示。第三步也需复核同步布尔接收契约。
- **来源：** [Feature1 技术设计 §4.5](./里程碑1/feature1-基本聊天页面.md#45-消息暂用-idrole-和-text-表达)、[§4.4](./里程碑1/feature1-基本聊天页面.md#44-用同步布尔回调表达本步的接收结果)。

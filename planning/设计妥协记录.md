# 设计妥协记录

记录为了当前范围而接受的简化，以及后续重新评估的时机。后续设计先检查是否触发对应条件；“更好的做法”是届时讨论的方向，不是提前要求实现的新架构。

第一步基础聊天页已完成并合并，[页面设计](./里程碑1/feature1-基本聊天页面.md)保留参考。当前[第二步单会话流式聊天](./里程碑1/README.md)合并原第二、三步；下列涉及消息归属、异步提交和服务接入的条件已触发，须在第二步设计中重新核对。

## 1. 当前对话暂保存在后端内存

- **妥协点：** 本期对话不落盘，后端进程重启后聊天内容和运行状态无法从内存恢复。
- **已确认的设计：** 唯一当前对话的用户消息、模型回复与运行状态由后端内存持有；网页保留草稿与展示状态，刷新或重连后先取后端当前内容与生成状态，再接收增量。关闭网页不自动取消生成；已保存的凭据仍在 JSON 文件中。这是已批准的替代方案，尚未实现到当前基础页面。
- **设计沿革：** 第一步 Feature1 仅验证输入、发送与显示，由 `ChatPage` 保存页面消息，刷新后清空；第二步设计中，用户已确认将消息与运行状态归属转到后端，并在刷新或重连后恢复。
- **为什么这样设计：** 本期先形成单一当前对话的完整流式聊天；磁盘持久化与历史回看按第七步推进，不提前引入多会话管理。
- **更好的做法：** 将对话记录与运行状态保存到本机磁盘，重启后读取并明确标记中断状态；草稿的恢复另按实际需求设计。
- **解决时机：** 第七步：本地存储与历史回看。
- **来源：** [当前单会话聊天规划](./里程碑1/README.md)、[原 Feature1 技术设计 §4.3](./里程碑1/feature1-基本聊天页面.md#43-草稿归-lexical发送后的消息归-chatpage)。

## 2. 暂用 Vite 开发服务提供页面

- **妥协点：** 当前入口依赖前端开发服务，还没有与本地 Agent 服务组成完整应用入口。
- **当时的设计：** 用现有 Node.js 和 npm 运行 Vite，浏览器打开本机开发页面。
- **为什么这样设计：** Feature1 尚无后端，不必为展示页面先建设完整本地服务。
- **更好的做法：** 本地服务形成后，评估由本地应用提供构建后的网页及业务接口，形成一致的启动方式；开发时仍可保留 Vite。
- **解决时机：** 第二步交付已触发：确定网页、本地 HTTP 和 WebSocket 的开发接入与应用启动方式。需要让别人直接启动使用、无需理解前端开发工具时解决完整入口问题。
- **来源：** [Feature1 技术设计 §4.1](./里程碑1/feature1-基本聊天页面.md#41-使用-react--typescript--vite在-web-内组织网页代码)。

## 3. 提交和消息内容暂时只表达普通文字

- **妥协点：** 字符串不能完整表达引用目标，当前消息类型也只有用户角色。
- **当时的设计：** 输入接口为 `onSend(text: string): boolean`，消息使用 `{ id, role: 'user', text }`；普通用户文字按原文展示。
- **为什么这样设计：** Feature1 没有模型回复和引用标签产生的数据，只需提交和展示文字。虽然已经选用 Lexical，仍不提前建立引用数据结构。
- **更好的做法：** 引入对应功能时，按实际需要扩展消息角色、结构化内容和提交接口；引用标签应携带目标信息，不能只保存可见名称。异步服务的接收结果与后续运行结果也要分别设计。
- **解决时机：** 第二步交付已触发：加入 AI 回复、运行状态并复核异步提交接收契约；引用标签仍在其对应功能阶段一并设计编辑内容、提交接口与消息展示。
- **来源：** [Feature1 技术设计 §4.5](./里程碑1/feature1-基本聊天页面.md#45-消息暂用-idrole-和-text-表达)、[§4.4](./里程碑1/feature1-基本聊天页面.md#44-用同步布尔回调表达本步的接收结果)。

## 4. 生成期间暂不支持排队发送

- [ ] **后续待办：** 支持生成期间继续发送消息，由后端保留排队输入，当前回答结束后依次正常调用模型；补齐排队状态、处理顺序和队列取消规则。具体排期未定，不作为第二步交付的完成条件。
- **妥协点：** 当前回答尚未结束时，用户可以编辑下一条草稿，但必须等待后才能发送。
- **本期设计：** 采用 A：生成期间前端暂时禁用发送，后端对并发提交明确拒绝；完成或失败后恢复发送，未被接受的草稿由前端保留。该规则只限制生成中的并发，不按消息内容或编号去重。
- **为什么这样设计：** 用户明确选择先完成基础单会话流式聊天，暂不增加消息队列及其界面状态，以控制本期复杂度。
- **更好的方向：** 采用用户期望的 B：允许提前提交下一条消息，后端按顺序执行，而不是同时并发请求模型；相关状态与取消行为在后续队列功能中一起设计。
- **解决时机：** 后续消息输入体验迭代，具体排期未定；开始引入排队输入时重新评估并替换本期限制。
- **来源：** 用户于 2026-10-28 确认本期采用 A，并要求记录 B 为后续待办；见[单会话聊天规划](./里程碑1/README.md)。该条记录设计选择，尚未实现到当前页面。

## 工具参数 JSON 暂不自动修复

- **妥协点：** 参数文字内存在非法转义或未转义控制字符时，部分 Pi 能有限修复的内容，本项目会记录为解析失败。
- **当前做法：** 空参数文字按 `{}` 接收；非空文字严格解析为 JSON 对象。失败时保留调用，以 `argumentsError` 记录原因和原始参数，不修复转义、不补齐截断结构；具体工具参数校验仍留给执行前处理。
- **原因：** 用户明确选择先用标准解析完成本期后端工具接入，减少兼容分支，并保留清楚、可复查的失败信息。
- **更好的方向：** 真实数据证明有必要时，评估引入 Pi 对字符串转义和控制字符的有限修复；继续拒绝结构截断，不推测字段或补齐任务内容。
- **解决时机：** 后续真实模型调用反复因上述可修复问题失败、影响正常使用时重新讨论；本期不自动启用修复。
- **来源文档与章节：** [Feature3 技术决策 §4.6](./里程碑1/feature3-工具定义与调用接收.md#strict-tool-arguments)、风险 2、验收案例 3。该选择已在本会话明确批准，尚未实施。

# 里程碑2：可实际使用的 Coding Agent

## 目标

在里程碑一的基础上，将最小可运行 Agent 完善为用户能实际用于编程的 Coding Agent：能理解项目和任务，读取、查找及修改代码，执行命令、运行项目与测试，并根据真实结果继续工作。用户能够选择模型和权限模式，使用 Skill、MCP 和长期 Memory，在任务中补充要求、查看改动，并在失败后继续推进。

本期重点是补齐完成真实编程任务所需的配套能力，让 Agent 在工程上稳定、可理解、可控制。能够完成真实任务是交付目标，不以配置入口齐全、模型能聊天或工具能单独调用作为完成依据。

当前已确认以下十项需求及推进顺序，尚未设计、实现或验收。本文件只记录目标、需求和完成标准；具体技术方案、交互细节及尚未确认的规则，在开展对应步骤时再讨论。

## 与其他里程碑的关系

- **里程碑一：** 完成基础 Agent 闭环，以及上下文压缩、Session 隔离、项目说明加载与上下文组织、本地保存和历史回看。第二期在这些能力上继续完善，不重复安排。
- **里程碑二：** 补齐用户完成真实编程工作所需的能力，以及开发者定位问题、迭代产品所需的排障设施。
- **里程碑三：** 通过 Terminal Bench 等评测检查和提升任务完成表现，进一步优化任务完成率与效果。本期不建设固定任务的评测平台，但各项功能仍需真实验收。

## 使用方式与边界

继续沿用本地网页和本机 Agent 的使用方式。用户配置所需模型的 API Key，选择项目、会话、模型和权限模式后提出编程任务，通过页面查看执行过程、实际结果及代码改动，并在需要时参与决策。

开发排障平台供我们在开发和迭代时按需接入。普通用户下载安装项目后，不需要配置 Langfuse 或其他日志平台的 Key，也不依赖外部排障平台才能使用 Agent。

以 Pi 的整体设计为主要参考，其他本地参考项目作为补充。每项能力开展设计时，再核对相关源码并说明取舍；本文件不提前规定 SDK、存储格式、协议实现、权限隔离方式或模块结构。

## 范围

| 顺序 | 能力 | 本里程碑需要做到 |
| --- | --- | --- |
| 1 | 开发排障与运行记录 | 开发者能读取故障日志、追查一次任务的执行过程，借助 Agent 分析并定位问题，支持后续修复与验证 |
| 2 | 多模型供应商与模型切换 | 支持已确认的九家供应商，统一通过 API Key 接入；正式支持的模型均经过真实链路验收，可在任务结束或中止后切换 |
| 3 | 权限管理 | 提供只读、需要审批、无需审批三种模式，实际执行遵守用户选择的权限 |
| 4 | Skill | 能发现、读取、使用及创建 Skill，使其中的做事方法在真实任务中发挥作用 |
| 5 | MCP 客户端 | 能配置和连接外部 MCP 服务器，发现并使用其能力，跑通至少一个真实服务的完整任务 |
| 6 | 长期 Memory | 能在日常工作中积累和找回有用信息，支持查看、更新、删除和按适用范围隔离 |
| 7 | 完整的终端任务管理 | 能执行短命令和持续运行的命令，查看状态与输出，并继续操作或停止对应命令 |
| 8 | 代码改动查看与安全恢复 | 用户能知道 Agent 改了什么，并在需要时安全恢复相关改动，保护用户原有修改 |
| 9 | 人机协同 | 用户能在运行中补充或纠正要求，Agent 能在需要关键决策时提问，并在获得回答后继续 |
| 10 | 失败后继续与运行限度管理 | 保留已完成工作和真实状态，支持失败后继续，并对持续运行和反复尝试提供可理解的控制 |

## 推进步骤

### 第一步：开发排障与运行记录

目标：出现问题后，我们能找到相关任务及执行记录，理解发生了什么，并让用于排障的 Agent 读取这些材料、结合源码分析问题，辅助修复和验证。

- [ ] 能追查一次任务中的模型请求、工具操作、关键输入与输出、状态、耗时和错误，并区分不同会话与任务。
- [ ] 记录能被开发者及用于排障的 Agent 查找和读取，足以帮助区分模型、工具、服务和页面等环节的问题。
- [ ] 开发时可选接入外部排障平台；Langfuse 是候选，不预先锁定产品。未配置或平台不可用时，不影响普通用户使用 Agent。
- [ ] 密钥和不应上传的内容受到保护，不因排障记录而暴露。
- 完成标准：通过一次实际故障，找到对应运行记录和出错环节，结合相关代码给出有依据的原因分析，并能在修复后核对结果。仅有日志列表或最终报错不算完成。

### 第二步：多模型供应商与模型切换

目标：用户能使用主流供应商提供的模型完成编程任务，并在同一会话中切换模型继续工作。

供应商范围已确定为九家：

| 范围 | 供应商与模型系列 |
| --- | --- |
| 国外 | OpenAI／GPT、Anthropic／Claude、Google／Gemini、Mistral |
| 国内 | Moonshot／Kimi、阿里／千问、MiniMax、DeepSeek、智谱／GLM |

- [ ] 九家统一通过 API Key 接入，沿用本机保存密钥的使用方式；首版不包含订阅账号登录。
- [ ] 用户能配置所需供应商、选择其支持的模型，并查看实际使用的供应商与模型。
- [ ] 每个正式声明支持的模型，都按现有 DeepSeek 的支持程度验证真实链路，包括流式回复、工具调用、连续多轮执行、中止和错误处理，并验证与上下文压缩的配合。模型提供的思考内容及用量如实处理，不伪造未提供的数据。
- [ ] 任务结束或中止后可以切换模型，保留当前会话和已有聊天、工具记录；正在执行的任务固定使用原模型。
- [ ] 切换后能够继续原任务，妥善处理历史兼容和不同上下文容量带来的限制，并向用户说明无法继续的原因。
- 完成标准：具体支持型号在本步开展时确认，每个正式支持型号均留下真实验收结果；另验证跨供应商切换后继续任务。配置成功、出现在模型列表或单独聊天成功，都不能替代完整验收。

### 第三步：权限管理

目标：用户能根据任务需要，选择 Agent 可以采取行动的方式，并理解实际允许的操作范围。

- [ ] **只读模式：** 可以查看、分析信息，不能执行改变受保护数据的操作。
- [ ] **需要审批的模式：** 需要批准的操作在执行前等待用户决定；用户能理解请求的操作，批准或拒绝后得到真实结果。
- [ ] **无需审批的危险模式：** 用户明确选择后，操作不再逐次请求审批，页面如实展示执行过程与结果。
- [ ] 所选模式对文件操作、命令执行以及 Skill、MCP 使用的相关能力一致生效，不能换一种工具绕过限制。
- 完成标准：分别验证三种模式的实际行为，包括允许、拦截、等待批准和拒绝后的结果。具体哪些操作需要审批、批准的有效范围及权限隔离方案，在本步设计时确定。

### 第四步：Skill 的发现、读取、使用与创建

目标：Agent 能使用已有 Skill 中的方法完成工作，也能根据用户需要创建可实际使用的 Skill。

- [ ] 能发现可用 Skill，并让用户和 Agent 了解其用途。
- [ ] 能在相关任务中读取并遵循 Skill，用户也能明确指定使用某项 Skill。
- [ ] 能使用 Skill 附带的说明、参考材料或脚本，并遵守当前权限模式。
- [ ] 能按用户要求创建或修改 Skill，之后重新发现并使用它。
- 完成标准：使用一个已有 Skill 完成真实任务，再创建或修改一个 Skill，并通过后续任务验证其实际作用。不能只以生成文件、列出名称或声称已加载作为完成依据。

### 第五步：MCP 客户端与真实服务接入

目标：Agent 能通过 MCP 使用外部服务，让外部工具参与现有任务执行过程。

- [ ] 用户能配置所需服务器，了解连接状态及可用能力；失败时能看到可处理的原因。
- [ ] Agent 能发现服务器提供的能力、发送调用、接收真实结果，并根据结果继续工作。
- [ ] 外部操作遵守当前权限模式，连接或调用失败不被当成操作成功。
- [ ] 至少接入一个真实服务，完成从用户提出需求到实际结果可核对的完整流程；优先考虑 Google 相关服务，具体服务和任务在本步开展时确定。
- 完成标准：核对服务器实际收到的调用、返回给模型的结果，以及任务最终产生的真实效果。仅能连接或列出工具不算完成，也不要求一次覆盖 Google 全家桶。

### 第六步：长期 Memory

目标：Agent 能把日常工作中值得保留的信息积累下来，并在之后的相关任务中找回使用，减少用户重复说明。

- [ ] 明确哪些信息值得记、何时写入和读取，以及如何保存、更新、纠正和删除。
- [ ] 用户能查看已保存的信息，并了解其来源与适用范围。
- [ ] 区分项目专属信息和可跨项目复用的信息，避免不同项目之间错误混用。
- [ ] 在新会话中按任务需要找回相关信息，与里程碑一的历史保存和上下文压缩配合。
- 完成标准：在一次工作中留下有用信息，新会话中能够找回并帮助完成相关任务；同时验证隔离、纠正和删除。自动积累的范围、是否需要确认及具体存储检索方式，在本步设计时确定。

### 第七步：完整的终端任务管理

目标：Agent 能照看自己启动的命令，既能运行测试等会结束的操作，也能管理开发服务等持续运行的操作。

- [ ] 能启动命令，查看执行中的状态、输出以及结束结果。
- [ ] 对需要持续运行的命令，能在其运行期间继续其他工作，之后再查看输出、继续交互或停止对应命令。
- [ ] 能区分命令启动、服务可用、正常结束、失败和被停止，不将尚未完成的操作报告为成功。
- [ ] 用户停止任务或退出使用时，相关命令的状态和处理结果清楚，避免留下无人管理的进程。
- 完成标准：运行一个有明确结果的命令，再启动一个持续运行的服务；Agent 在服务运行期间继续工作，之后能找回其状态、读取新输出并停止它。具体交互方式和进程保留规则在本步设计时确定。

### 第八步：代码改动查看与安全恢复

目标：用户能看清 Agent 对项目做了哪些改动，并在需要时恢复相关内容。

- [ ] 能查看任务涉及的文件变化及具体内容差异。
- [ ] 任务结束后说明改了什么、做过哪些验证，以及仍有哪些未解决的问题。
- [ ] 能恢复相关改动，同时保护用户在任务开始前已有或任务期间自行做出的修改。
- 完成标准：在带有用户原有修改的项目中完成代码改动，核对差异，再恢复指定的 Agent 改动，确认用户原有内容未被误覆盖。改动归属、恢复范围和冲突处理方式在本步设计时确定。

### 第九步：人机协同

目标：用户能在 Agent 工作时调整方向，Agent 也能在缺少关键决定时及时向用户提问。

- [ ] 任务运行期间，用户能补充要求或纠正方向，并了解这些要求是否被接收和采用。
- [ ] Agent 遇到影响结果的关键歧义时，能提出清楚的问题，在得到回答后继续工作。
- [ ] 补充指令、回答问题和已有任务进度能够衔接，已经发生的操作如实保留，不因新要求被改写成未发生。
- 完成标准：在真实编程任务中途补充一项要求，验证后续行为遵循更新后的要求；再验证 Agent 提问、等待回答并接续工作的过程。消息如何排队、何时生效及如何等待，在本步设计时确定。

### 第十步：失败后继续与运行限度管理

目标：模型或工具失败后，用户能理解当前情况，保留已有工作并继续推进；持续运行与反复尝试有可理解的控制方式。

- [ ] 保留已完成的代码改动、工具结果和任务进度，明确失败位置及尚未完成的工作。
- [ ] 用户能在解决问题、重试或切换模型后继续任务，无须重新描述全部背景。
- [ ] 继续执行时区分尚未执行、已经成功和结果不明的操作，避免盲目重复已发生的文件修改或外部操作。
- [ ] 对持续运行时间、反复调用或费用等运行限度提供可见、可控制的管理方式，达到限制时保留已有结果并说明原因。
- 完成标准：在真实任务中制造可核对的模型或工具失败，处理后继续完成任务，确认已有成果保留且操作未被错误重复；验证达到运行限制时能明确结束或等待处理。重试规则、限制项和默认值在本步设计时确定。

## 整体验收

在真实项目中，从实际网页入口提出一项有明确完成条件的编程任务，验证 Agent 能取得项目背景、查找和读取代码、修改文件、执行所需命令与测试，并根据真实结果继续工作。用户能查看改动、参与关键决策，任务完成后能核对实际成果和验证结果。

结合各步骤的独立验收，检查多模型、权限、Skill、MCP、Memory、终端任务、改动恢复、人机协同和失败后继续是否能与基础 Agent 共同工作。通过开发排障记录，能追查实际故障并辅助修复。各正式支持模型均需有真实验收记录，不以某一家通过代表其他模型已经通过。

真实任务和具体案例在相应步骤开展时选择，不提前编造项目背景或结果。缺少凭据、服务接入条件或实际验证时，明确记录未完成的项目，不能将演示、假数据或模型自述当作验收通过。

## 首轮请求与候选目录

<a id="case-01"></a>

### 01 MCP 已连接时首轮只提供服务提示与搜索入口

- **类型**　集成测试，受控模型与已连接的 MCP 目录。
- **目的**　确认新会话首轮将未加载工具留在后端。
- **怎么测**　启用已发现工具的 GitHub 与 Notion，新建会话并发送普通问题。捕获首个实际模型请求。系统提示包含服务名、搜索方式和可用的一行简介。结构化声明包含原有工具与 `tool_search`，两个服务的具体工具定义均为零。检查首轮可正常回答，远端工具调用次数为零。用含换行和长说明的受控服务核对取首行及提示段长度边界。

<a id="case-02"></a>

### 02 无启用服务时省略 MCP 搜索入口

- **类型**　集成测试。
- **目的**　确认搜索随 MCP 功能在普通会话中按需出现。
- **怎么测**　保存一个服务并停用，开启新会话。检查实际模型请求里的 MCP 服务提示、`tool_search` 和远端工具定义均为零，普通工具仍可工作。

<a id="case-03"></a>

### 03 搜索等待已开始的工具发现

- **类型**　集成测试，受控 HTTP MCP 服务。
- **目的**　确认慢连接在首次搜索时可用，同时首轮模型请求可先开始。
- **怎么测**　启用一个服务并延迟 `tools/list` 返回。首轮模型应在放行前收到该服务名和 `tool_search`，随后发起搜索。放行工具列表后，核对使用这份目录返回匹配结果。确认只使用管理器已经开始的连接，搜索发起的额外握手次数为零。

## 搜索规则与下一轮调用

<a id="case-04"></a>

### 04 默认搜索按 Pi 规则排序并最多加载八项

- **类型**　单元测试。
- **目的**　确认搜索采用 Pi 的关键词排序和缺省数量。
- **怎么测**　准备至少 9 个能命中的构造定义，使用包含精确工具名、多个搜索词、参数字段名与描述词的查询对照 Pi 的排序测试。核对精确名称优先，其他候选按关键词覆盖和相关性排序。省略 `limit` 时结果最多 8 项，已在声明中的工具不参与排名。

<a id="case-05"></a>

### 05 显式 limit 控制本次加载数量

- **类型**　单元测试。
- **目的**　确认 8 是默认值，调用可以指定另一个正整数。
- **怎么测**　用可返回至少 10 项的目录执行一次 `limit: 10` 的搜索。核对按排名取前 10 项，修改 `limit` 后重新从同一初始目录运行可得到相应数量。

<a id="case-06"></a>

### 06 无效参数不会加载工具

- **类型**　单元测试，按无效输入分别运行。
- **目的**　确认搜索校验不会产生部分加载。
- **怎么测**　分别提交空白关键词、非正数上限和小数上限。每次检查返回参数错误，候选搜索和新增加载均为零。

<a id="case-07"></a>

### 07 无匹配时可换关键词继续搜索

- **类型**　集成测试，受控模型。
- **目的**　确认空结果可以在同一任务内恢复。
- **怎么测**　让模型先发出无匹配的查询，核对对应调用编号收到无匹配，下一轮仍保留搜索入口且没有新增远端定义。让模型换成能命中的关键词，核对命中工具随后进入声明。

<a id="case-08"></a>

### 08 下一轮声明命中工具并完成远端调用

- **类型**　端到端测试，Chromium、本机 SI、受控模型和 MCP 服务。
- **目的**　从现有网页入口验证请求、搜索、远端执行和可见结果的闭环。
- **怎么测**　提交读取测试 Issue 的任务。捕获首轮的搜索调用与结果，核对结果正文只有命中工具名称和简述。下一次请求仅加入命中工具的完整名称、描述和参数规则，其他远端定义数量为零。让模型调用命中工具，核对远端参数、结果内容、原调用编号及网页结果卡。

<a id="case-09"></a>

### 09 同一批提前调用未声明工具被拦截

- **类型**　集成测试，受控模型返回同批调用。
- **目的**　确认搜索只改变下一轮工具声明。
- **怎么测**　首轮让模型同时提交 `tool_search` 和尚未声明的 `mcp__github__issue_read`。核对搜索结果正常保存，提前调用按自己的编号回填未声明错误，远端收到的请求次数为零。下一轮收到并调用正式定义时远端才收到请求。

<a id="case-10"></a>

### 10 停止任务会取消本次搜索等待

- **类型**　集成测试，受控 MCP 服务。
- **目的**　确认中止边界仅影响本次会话的等待。
- **怎么测**　在搜索等待工具列表时停止任务，再放行远端工具发现。核对已停止任务的新增加载及后续模型请求数均为零。共享目录仍可就绪，之后的新任务可以发起新的搜索。

## 会话加载记录

<a id="case-11"></a>

### 11 同一会话追问时保留已加载工具

- **类型**　集成测试，受控模型。
- **目的**　确认加载跨用户消息继续有效。
- **怎么测**　在一个会话中完成首次搜索并结束该条消息的任务。发送下一条追问，核对首个请求已包含上次命中的定义。让模型直接使用该工具，核对能正常调用且搜索次数仍为首次的一次。

<a id="case-12"></a>

### 12 后端重启后恢复原会话的有效工具

- **类型**　集成测试，临时 SQLite 与真实后端重启。
- **目的**　确认工具随原会话恢复，并使用重新发现的定义。
- **怎么测**　成功加载一个测试工具后关闭后端。在保留服务配置的前提下让远端更新工具参数说明，然后重启。目录尚未就绪时，模型请求里该工具的旧定义数量为零。目录就绪后继续原会话，核对已加载工具按新的参数定义声明且可直接使用。

<a id="case-13"></a>

### 13 压缩后保留已加载工具

- **类型**　集成测试，受控模型与会话压缩。
- **目的**　确认上下文裁剪不会丢失会话的加载状态。
- **怎么测**　加载工具后增加对话历史，执行压缩并核对原搜索消息已离开保留窗口。提交追问，检查工具仍能从已提交记录加载，历史里仍保留的工具调用和结果按原编号配对。

<a id="case-14"></a>

### 14 其他会话从自己的加载记录开始

- **类型**　集成测试，临时 SQLite。
- **目的**　确认共享目录不会共享加载状态，旧库可以按空集合恢复。
- **怎么测**　会话 A 成功加载，打开使用相同 MCP 服务但没有加载记录的旧会话 B。核对 B 的首个请求只能使用发现入口，A 的已加载工具声明在 B 中为零。再次回到 A，核对原记录仍有效。

<a id="case-15"></a>

### 15 搜索结果保存失败时加载一并回滚

- **类型**　集成测试，注入 SQLite 写入失败。
- **目的**　确认工具结果与加载状态由同一提交决定。
- **怎么测**　让搜索命中后、提交成功前事务失败。核对网页走原有保存失败反馈，后续模型请求没有获得这次命中的定义。重开库确认搜索结果和加载记录都没有被提交。

## 权限、连接与目录更新

<a id="case-16"></a>

### 16 权限受限时撤下搜索和远端工具

- **类型**　集成测试，分别复用只读及计划模式入口。
- **目的**　确认已加载或猜中的 MCP 工具不扩大权限。
- **怎么测**　先在普通模式加载工具，再切到既有的只读或计划模式。核对新请求排除 MCP 提示、搜索入口和已加载定义。受控模型尝试调用旧工具名称时，核对调用被拦截，远端调用次数为零。

<a id="case-17"></a>

### 17 替换同名服务配置后旧加载记录失效

- **类型**　集成测试，受控 MCP 服务。
- **目的**　确认工具名相同也必须匹配原服务与连接配置。
- **怎么测**　成功加载某工具后更换服务地址和凭据，在新地址提供同名工具。检查旧加载记录不授予新工具声明，模型沿用旧名字的调用不会发送到新地址。重新搜索以后才允许调用新绑定。

<a id="case-18"></a>

### 18 已加载工具沿用后台恢复与停用规则

- **类型**　端到端回归，复用 Chromium 本机 MCP 场景及底层集成测试。
- **目的**　确认披露方式变化后，连接生命周期和执行语义沿用 Feature 5。
- **怎么测**　在已加载工具执行期间切断受控连接，核对后台发起恢复，结果未知的原调用只回填一次。服务在重连时仍提供同名工具，核对后续请求直接声明并调用新定义，无需重新搜索，结果按原编号回填。沿用同一回归场景的下一次断开，令恢复耗尽，核对开关关闭、后续请求撤下工具。另按现有管理器测试复跑主动停用和明确协议会话过期分支。

<a id="case-19"></a>

### 19 同一配置重新启用时只恢复仍有资格的工具

- **类型**　集成测试，受控 MCP 服务。
- **目的**　确认服务开关即时约束工具可见性，重新启用后只恢复资格仍有效的工具。
- **怎么测**　在同一会话已加载两项工具。先用成功的目录刷新确认其中一项撤下，再停用服务，核对停用期间两项工具均未声明、旧调用均未发往远端。用原配置重新启用，远端重新提供两项工具。核对原本仍有资格的工具使用最新定义，曾撤下的工具仍需重新搜索。

<a id="case-22"></a>

### 22 通知刷新后下一轮使用新定义

- **类型**　集成测试，受控模型与支持通知的 MCP 服务。
- **目的**　确认服务无需断线即可更新已加载工具的定义。
- **怎么测**　加载一个工具。让服务保持连接并修改该工具的描述和必填参数，然后发送 `notifications/tools/list_changed`。核对后端拉取新列表，目录更新完毕后的第一轮模型请求包含新定义。让模型直接调用，核对远端收到新参数，搜索和重新握手次数均为零。

<a id="case-23"></a>

### 23 同一连接串行刷新且只发布有效结果

- **类型**　集成测试，受控 MCP 服务与可延迟的目录响应。
- **目的**　确认通知连发、刷新失败或替换连接时目录保持正确。
- **怎么测**　挂起第一次刷新后连发多条通知，核对同时只有一次列表请求。放行后核对只补一次刷新，最后使用最新结果。让一次刷新失败，核对保留上一份成功目录及已加载记录。另挂起旧连接的刷新并替换连接或配置，待新目录就绪后释放旧响应，核对目录和已加载资格均未被旧响应改变。

<a id="case-24"></a>

### 24 确认撤下后同名工具须重新搜索

- **类型**　集成测试，受控 MCP 服务、会话持久化与后端重启。
- **目的**　确认成功目录中的工具撤下会清除其加载资格。
- **怎么测**　在两个会话加载同一工具，再关闭其中一个会话。让服务通知变更并成功返回缺少该工具的完整列表，核对后续模型请求撤下该定义。用同一连接配置重新上架同名工具，核对仍打开的会话未自动声明该工具。重启后端并打开两个会话，两者均须重新搜索才能再次调用。核对原来的搜索文本和调用结果仍可从会话历史读取。另验证只有在后端启动后第一次拉取目录时才发现工具已撤下的情况。

<a id="case-25"></a>

### 25 发送前按当前目录复查旧调用

- **类型**　集成测试，受控模型和 MCP 服务，复用发送前检查入口。
- **目的**　确认模型按旧定义生成的调用在实际发送前受当前目录约束。
- **怎么测**　在模型收到工具定义后、发送远端调用前挂起请求，分别发布工具撤下、工具仍在但旧参数失效两种目录，再放行。核对旧调用没有发送，失败按原调用编号回填，下一轮声明使用最新目录。另将更新安排在远端已经收到调用之后，核对刷新不会重发请求，原结果只回填一次。

## 真实任务与输入开销

<a id="case-20"></a>

### 20 真实模型自行找到 GitHub 工具并读取 Issue

- **类型**　端到端测试，正式网页、GitHub 只读 MCP 及真实模型。
- **目的**　验证用户用自然语言提出 Issue 任务后，模型能自行找到和调用正确的工具。
- **怎么测**　在独立测试配置启用 GitHub，开新会话，只给 Issue 链接并要求读标题、状态和链接。核对搜索先发生，命中工具随后进入实际请求，再核对远端参数、返回值和回答与 GitHub 原记录一致。按执行说明记录请求用量。

<a id="case-21"></a>

### 21 真实模型自行找到 Notion 工具并读取页面

- **类型**　端到端测试，正式网页、真实 Notion 授权及真实模型。
- **目的**　验证 GitHub 与 Notion 共用目录时能从中文任务找到正确的服务和工具。
- **怎么测**　GitHub 与 Notion 均启用并完成既有授权流程后，开新会话，只让模型读取本项目已用于真实验收的「一些想法」测试页。核对首轮尚未声明两家具体工具。验证搜索命中和后续调用属于 Notion，原调用与工具结果对应，实际内容和回复中的标题、链接与测试页一致。按执行说明记录请求用量。

## 下一轮排队

<a id="case-01"></a>

### 01 当前任务完成后，排队消息依序开启新任务并采用启动时的模型

- **类型** 端到端测试（Chromium、受控模型服务）。
- **目的** 验证网页显示的待发顺序及模型选择与服务端实际启动一致。
- **怎么测** 用 DeepSeek Flash、低推理强度启动 A，在收到第一条模型请求后挂起响应。在同一会话依次发送 B「补写 README」和 C「检查 README」，刷新网页，核对服务端尚只有 A 在运行，队列仍为 B、C。切到 Kimi K3、高推理强度，让 A 返回一次读取工具调用再结束。核对 A 携带读取结果发出的下一次模型请求仍使用 DeepSeek Flash、低推理强度。A 完成后，B、C 各自开启新任务，并在各自启动时采用 Kimi K3、高推理强度，B 完成后才有 C 的首个模型请求。每条待发项在启动时从队列消失，在历史中各出现一次。

<a id="case-02"></a>

### 02 编辑纯文本条目保留原位置和编号

- **类型** 端到端测试（Chromium、受控模型服务）。
- **目的** 验证行内修改只改变待发文本，且丢失初次回执后的重试不会覆盖编辑。
- **怎么测** 挂起支持图片的 A，依次排入 B「原说明」、带图片和文字「这个呢」的 C、只有图片的 D。核对 C 显示 `[image] 这个呢`，D 显示 `[image]`，两条的编辑按钮均禁用，删除按钮均可用。打开 B 的行内编辑，输入「临时说明」并取消，检查 B 仍显示「原说明」。再次编辑，将 B 保存为两行「第一行说明」「第二行说明」。确认原 B 编号和位置仍在，三项行内操作恢复。用原提交编号和原提交内容重试 B，确认仍只存在同一条已编辑项。让任务接续，检查 B 新任务的模型输入保留两行文字。

<a id="case-03"></a>

### 03 整条删除含图待发项后，其余消息按原序启动

- **类型** 集成测试（真实 HTTP、WebSocket、SQLite，受控模型服务）。
- **目的** 验证服务端拒绝编辑含图条目，并按指定编号删除整条消息。
- **怎么测** 挂起支持图片的 A，依次排入 B、C、D，其中 B、C 文本相同且编号不同，C 还带图片。直接向服务端提交对 C 的文本编辑，核对请求被拒绝，C 的编号、位置、原图和文字均保留。按 C 的编号删除，核对快照及重订阅只剩 B、D，服务端对 C 的旧提交重试也未创建新条目。释放 A 后检查仅启动 B、D。对已启动的 B 再发删除请求，核对服务端给出其实际状态，已开始的任务照常收尾。

<a id="case-04"></a>

### 04 任务最终失败后等待新发送才恢复队列

- **类型** 集成测试（会话层、SQLite、受控模型）。
- **目的** 验证最终失败会暂停队列，并保留已完成工作。
- **怎么测** 让 A 先写入 `done.txt`，挂起接收该工具结果的后续模型请求。在这一请求进行中排入 B、C，提交插话 S 并确认它仍在等待。让请求最终失败。检查 A 的失败和已有写入结果仍可回看，重订阅后队列与 S 仍在等待，模型调用数保持不变。发送 D 后，检查 B 的首个模型请求按 S、B 的顺序收到新输入，C、D 随后各自启动，`done.txt` 的写操作只有一次。

<a id="case-05"></a>

### 05 队首启动保存失败后保留待发项

- **类型** 集成测试（会话层、SQLite、注入保存失败）。
- **目的** 验证队首领取和正式任务保存的一致性。
- **怎么测** 挂起 A，排入 B、C。让 A 正常完成，在尝试保存 B 的任务和首消息时模拟一次明确回滚。核对 B、C 仍按原序排队，暂停原因可见，模型没有收到 B、C，也没有留下 B 的半条历史。恢复保存并再次发送 D，确认按 B、C、D 启动。另用保存回执不确定的故障样本核对服务端在确认实际持久状态前不发出 B 的模型请求。

<a id="case-06"></a>

### 06 计划等待审核时排队项继续等待

- **类型** 集成测试（真实 HTTP、WebSocket、SQLite，受控模型服务）。
- **目的** 验证队列尊重已有的计划审核。
- **怎么测** 让 A 在计划模式下生成一份可审核的方案。A 返回方案前排入 B。A 完成时核对会话显示待审计划，B 仍待发送，模型没有收到 B。使用现有审核入口批准方案，检查先启动获准执行的方案任务。该任务正常完成后才启动 B。

<a id="case-07"></a>

### 07 正常关闭会清空本次已加载会话的待发项

- **类型** 集成测试（服务进程、SQLite、受控模型服务）。
- **目的** 验证正常关闭冻结新任务启动，并按已确认的会话加载范围清理。
- **怎么测** 准备两个含待发项的已保存会话，启动服务后只打开第一个。让加载的会话有一项可在收尾时尝试启动的待发任务，触发正常关闭。重启并查看两会话，确认关闭过程中未启动新的待发模型请求。已加载会话的未启动普通队列和待发插话已清空，原任务历史保留。此前未加载会话的待发记录仍在，打开后保持暂停。

<a id="case-08"></a>

### 08 意外退出后重开会话恢复已保存的待发项

- **类型** 集成测试（服务进程、SQLite、受控模型服务）。
- **目的** 验证进程中断能恢复已经确认的待发条目。
- **怎么测** 挂起 A 的首个模型响应，提交 B、C 和插话 S 并取得接收回执。让 A 返回提问工具调用，进入等待后强制结束该测试服务进程。使用原 SQLite 重启并订阅，检查 A 为「已中断」，原答题入口已关闭。B、C 和 S 仍待发且保持原编号，服务端没有自动开始新请求。发送 D 后，确认 B 的首个模型输入包含 S、B，C、D 后续各启动一次。

## 任务运行中插话

<a id="case-09"></a>

### 09 插话在整批工具收尾后进入同一任务

- **类型** 端到端测试（Chromium、受控模型服务）。
- **目的** 验证插话的发送反馈、进入模型的时机和历史位置。
- **怎么测** 让 A 发出两条工具调用，把第二条的返回挂起。从网页发送插话 S「保留旧接口」，短暂挂起 HTTP 请求，检查原文显示「正在提交」。放行后检查同一条原文显示「等待交给模型」。此时第一个工具可以完成，当前没有第二次模型请求。释放第二个工具，检查下一请求包含原序的两个工具结果，随后才是 S，当次请求的任务编号仍属 A。查看页面和服务重开后的历史，校对工具结果仍在原调用下，S 只有一条正式气泡且没有等待标记。

<a id="case-10"></a>

### 10 纯文字回复结束时有待发插话便继续当前任务

- **类型** 集成测试（会话层、SQLite、受控模型）。
- **目的** 验证即将结束的纯文字步骤也接得住插话。
- **怎么测** 让 A 流式返回「目前方案」，暂停在模型结束信号前。提交 S 并取得接收回执，放行结束信号。模型收到下一次请求时，核对「目前方案」在 S 前面，两次请求属于同一个任务，模型和推理强度相同。下一次请求正常结束后核对 A 只形成一个终态。

<a id="case-11"></a>

### 11 转为插话时搬移原排队条目及附件

- **类型** 端到端测试（Chromium、受控模型服务）。
- **目的** 验证队列上的箭头搬移的是完整原条目。
- **怎么测** 在支持图片的 A 运行期间排入纯文本 B 和带图片的 C，点击 C 行的转插话箭头。核对 B 仍在原排队位置，C 从待发区移到聊天区并显示等待，编号和图片相同。以 C 的编号重复转换，核对只存在一条待插话。释放 A 当前步骤，检查 A 的下一次模型请求包含 C 正文和图片。A 结束后只有 B 启动独立任务。

<a id="case-12"></a>

### 12 转换到达时任务已结束则保留原排队状态

- **类型** 集成测试（真实 HTTP、WebSocket、SQLite，受控模型服务）。
- **目的** 验证过期的转插话操作不会重排或重复消息。
- **怎么测** 在 A 运行时保留 B、C 的队列快照，令 A 中止并等到服务端闲置。再提交将 B 转为插话的操作，核对返回 B 仍待发及其原位置，B、C 顺序未变，没有模型请求。对于已领取的同编号，核对返回实际启动状态，历史中仍只有同一条原消息。

<a id="case-13"></a>

### 13 中止收尾期间点击转插话保留原队列位置

- **类型** 集成测试（真实 HTTP、WebSocket、SQLite，受控工具和模型）。
- **目的** 验证中止进行中时，转换操作仍保留原有先后顺序。
- **怎么测** 让 A 的工具接到中止信号后暂缓返回。排入 B、C，点击中止并等待信号到达。在工具完成收尾之前尝试转换 B，核对 B 仍在 C 前且仍是同一待发条目。放行收尾并再次发送 D，核对之后按 B、C、D 顺序处理。

<a id="case-14"></a>

### 14 中止后保留的插话依原序进入恢复任务

- **类型** 端到端测试（Chromium、受控模型服务）。
- **目的** 验证停止运行保留未交给模型的插话，并在恢复时展示真实顺序。
- **怎么测** 挂起 A，接收插话 S1、S2 并排入 B、C。点击中止，核对 A 显示结束，S1、S2 的原气泡仍等待，B、C 暂停。刷新并核对气泡和队列仍在。再次发送普通消息 D，核对第一个启动的任务由 B 开启，其首个请求中新输入的顺序为 S1、S2、B。C、D 其后各自启动。页面和会话记录里原任务历史及恢复后的输入顺序相同，每条输入均只出现一次。

<a id="case-15"></a>

### 15 空闲时直接插话启动同一会话的新任务

- **类型** 集成测试（真实 HTTP、WebSocket、SQLite，受控工具和模型）。
- **目的** 验证普通队列为空时直接插话使用新任务的接收路径。
- **怎么测** 令 A 中止并留下已确认但尚未加入模型请求的插话 S，普通队列为空。向同会话发送新的直接插话 D，检查只开启一个新任务，其首次请求按顺序携带 S 和 D。重试 D 的同一提交编号，检查没有第二个任务。

<a id="case-16"></a>

### 16 空闲且有普通队列时直接插话随队首进入模型

- **类型** 集成测试（真实 HTTP、WebSocket、SQLite，受控工具和模型）。
- **目的** 验证直接插话唤醒暂停队列，普通消息保持先后顺序。
- **怎么测** 令 A 中止，保留一条原有插话 S 和普通队列 B、C。在空闲状态直接发送插话 D。核对先启动 B，首个模型请求的新增输入顺序为 S、D、B，C 仍在普通队列中。

<a id="case-17"></a>

### 17 直接插话在中止收尾期间到达时进入普通队尾

- **类型** 集成测试（真实 HTTP、WebSocket、SQLite，受控工具和模型）。
- **目的** 验证中止期间的直接发送按恢复顺序执行。
- **怎么测** 在 A 运行时排入 B、C，让 A 的当前工具收到中止信号后暂缓收尾。直接发送带插话标记的 D，核对回执为已排队。放行原任务收尾，核对这次发送会恢复队列，B、C、D 依次各自启动。

## 反问、等待与补答

<a id="case-18"></a>

### 18 多题整组提交只回填一次并放行同批后续工具

- **类型** 端到端测试（Chromium、受控模型服务）。
- **目的** 验证多题、多选、逐题跳过与整组提交，同时保留同批工具及普通草稿。
- **怎么测** 留下未发送的普通草稿。让模型同批依次读取 `before.txt`、调用 `ask-1` 提出一组单选题、多选题和可自由输入的题，再读取 `after.txt`。第一项读取完成后刷新，核对同一组题目和原截止时间。第一题选 B，第二题勾 A、C 并输入补充文字，第三题跳过。提交前来回切题，核对已填内容和截止时间仍在，后续读取尚未开始。整组提交后仅产生一条 `ask-1` 的工具结果，包含三道题各自的 `id`、答案或跳过项。之后才按原参数读取 `after.txt`。下一次模型请求按原工具序收到三条配对结果，普通草稿仍可编辑。

<a id="case-19"></a>

### 19 等待期间整组跳过以未作答结束原工具

- **类型** 集成测试（真实 HTTP、WebSocket、SQLite，受控模型服务）。
- **目的** 验证跳过具有明确结果并且只能结算一次。
- **怎么测** 让 A 提出包含「是否更新旧接口？」的一组题。分别提交缺少题目、重复或未知的题号、无效选项、单选题多项答案和跨会话请求，核对均被拒绝且整组仍等待。提交每题 `selected: []` 且省略 `custom` 的整组答案，核对卡片关闭，原调用只收到一条工具结果，每题均为未作答。重复提交同一回复编号，核对没有第二条结果或补答消息。受控模型接到未作答结果后只执行独立读取，旧接口文件内容保持原样。

<a id="case-20"></a>

### 20 超时后整组跳过只关闭原问题组

- **类型** 端到端测试（Chromium、可控时钟和模型）。
- **目的** 验证超时后的主动关闭保留当时已写入的工具结果。
- **怎么测** 让 A 提出两道题并超时，等 A 完成且会话空闲。跳过第一题后确认第二题仍可回答。继续跳过第二题并提交整组，核对卡片关闭，原工具结果仍为「超时未答」，此操作没有新增模型请求。重开会话后继续显示原历史及关闭状态。

<a id="case-21"></a>

### 21 一直等待允许超过 120 秒后自由回答

- **类型** 端到端测试（Chromium、实际设置文件、可控时钟和模型）。
- **目的** 验证本机设置持久生效，已开始的等待按开始时选定的方式结算。
- **怎么测** 从缺少该字段的设置文件启动，打开网页「通用」，核对默认值为「等待 120 秒后继续」。从设置菜单选「一直等待回复」并重启，确认保存值仍在。让 A 省略 `timeout` 提问，核对当前问题没有截止时间。把设置改回 120 秒并推进服务端时钟超过 120 秒，检查这个问题仍等待。回到回答区自由填入「保留只读查询接口」，核对原工具结果记录该文本。下一次同样省略 `timeout`，核对 120 秒到期时返回超时。

<a id="case-22"></a>

### 22 跨过截止时间的回答作为运行中补答接收一次

- **类型** 集成测试（会话层、SQLite、可控时钟和模型）。
- **目的** 验证截止时间竞态只结算一次并保留实际请求顺序。
- **怎么测** 让 A 发起 `ask-1` 提出两道题，后续还有一个受控工具。尝试只提交第一题，核对服务端拒绝并保留等待。服务端时钟为开始后 119.999 秒时，将第一题的答案和第二题的跳过项从两条连接提交，把服务端裁定暂缓到 120 秒后。核对原调用只保存一条 `pending: true` 的超时结果，后续工具开始，服务端接收一条补答。放行后续工具后，核对 A 下一请求在匹配的工具结果之后包含一条用户消息，携带 `ask-1`、两道原题及其回答和跳过项。

<a id="case-23"></a>

### 23 已超时问题在服务重启和会话空闲后仍可补答

- **类型** 端到端测试（Chromium、服务进程、受控模型及时钟）。
- **目的** 验证服务重启后可在原问题卡分次填写，整组提交才启动新任务。
- **怎么测** 让 A 提出三道题并在超时后完成，会话无排队消息。重启服务并打开原会话，核对聊天输入区正常，原卡片可打开三道题。先填第一题的自由答案，隔一段时间再回答第二题。来回切题确认已填内容仍在，第三题尚未处理时无法提交，也没有新增模型请求。跳过第三题并提交整组，确认同一会话只开启一个新任务 B。B 的首个模型请求只收到一条补答用户消息，包含原调用编号、三道原题、前两题答案和第三题跳过项。A 的原工具结果仍为「超时未答」。刷新后原卡片已关闭，重复的回复编号不会启动另一个任务。

<a id="case-24"></a>

### 24 问题已超时后中止原任务仍可补答

- **类型** 端到端测试（Chromium、受控模型及时钟）。
- **目的** 验证中止任务后，已经记录为「超时未答」的问题仍可补答。
- **怎么测** 让 A 提问并超时。确认服务端已保存「超时未答」，原问题卡已开放补答，同时保持后续工具运行。此时中止 A，核对 A 为已中止且原卡片仍可补答。会话空闲后只提交补答，检查同一会话启动新任务，首个请求带有原问题和答案，A 的工具结果仍为「超时未答」。

<a id="case-25"></a>

### 25 等待中止后关闭答题入口并保留已做操作

- **类型** 端到端测试（Chromium、受控模型服务）。
- **目的** 验证停止原任务也会释放正在等待的问答。
- **怎么测** 让 A 先写入 `before.txt`，同批随后提问并准备写 `after.txt`。确认卡片进入等待后点击中止。核对任务结束、答题入口关闭，提问和前一条写入如实保留，`after.txt` 未写入，也没有下一次模型请求。刷新后对原问题发出的迟到回复应被拒绝。

<a id="case-26"></a>

### 26 手动任务可以反问且工作区权限继续生效

- **类型** 集成测试（会话层、权限检查、受控模型）。
- **目的** 验证提问的使用范围和回答对权限的影响。
- **怎么测** 在普通、计划和只读的手动任务中分别让模型调用同一测试问题，核对工具可见且答复回到原调用。让计划、只读任务在答复后尝试写入同一受保护文件，核对原权限检查拒绝，文件内容不变。触发一次定时任务，核对发往模型的工具列表没有反问工具。让受控模型仍尝试发起该调用，确认没有建立等待问题，定时任务可以收尾。

<a id="case-27"></a>

### 27 单次等待时长覆盖通用默认

- **类型** 集成测试（会话层、实际设置文件、可控时钟和模型）。
- **目的** 验证本次等待时长的优先级以及整组只使用一个计时器。
- **怎么测** 将「通用」设为一直等待，令模型以 `timeout: 30` 提出两道题。推进时钟到 29.999 秒，核对整组仍等待。推进到 30 秒，核对只返回一条超时结果，两题均可补答，通用默认仍为一直等待。再将通用默认改为 120 秒，令模型以 `timeout: -1` 提问，推进超过 120 秒后核对仍可正常回答。让模型分别传入 0、负数（`-1` 除外）、小数和超上限值，核对返回工具参数错误且网页未开启答题等待。

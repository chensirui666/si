## 会话初始化与提交

<a id="case-01"></a>

### 01 `session_start` 在会话首次处理输入前触发

- **类型** 会话集成测试，使用受控模型。
- **目的** 确认新会话完成扩展注册后，只触发一次 `session_start`。
- **怎么测** 使用测试扩展在 `session_start` 和 `input` 写入事件顺序。先在新会话发送能被扩展处理的 `ping`，再在同一个草稿发送正式消息。检查第一次 `input` 前已有一次 `session_start`，第二次提交继续使用同一个会话编号，整个过程只触发一次 `session_start`。

<a id="case-02"></a>

### 02 `input` 在保存用户消息前改写输入

- **类型** 会话集成测试，使用受控模型。
- **目的** 确认同一次有效提交先经过 `input`，再形成正式用户消息和模型输入。
- **怎么测** 提交原文 `A`。测试扩展记录 `input` 的次数并把文本改为 `B`。检查回调触发时，本次正式消息尚未写入。回执后核对模型首轮输入、服务端用户消息和重新读取的历史，三处均为 `B`，本次 `input` 只执行一次。

<a id="case-03"></a>

### 03 `before_agent_start` 结束并保存后才返回回执

- **类型** HTTP 与会话集成测试，使用受控模型。
- **目的** 确认启动 Hook 每项任务触发一次，并在原有发送回执之前完成。
- **怎么测** 从 `/api/sessions/start` 发出首条普通消息。测试扩展进入 `before_agent_start` 后暂停在一个可由测试解除的等待点。等待时检查成功回执尚未返回，会话列表尚未加入正式会话，模型调用次数为零。解除等待后检查回调先结束，回执返回时已能从存储读回正式消息和任务。本任务的 `before_agent_start` 只触发一次。

## 模型轮次与上下文

<a id="case-04"></a>

### 04 `turn_start` 在每轮模型请求前触发

- **类型** Agent 与会话集成测试，使用受控模型和工具。
- **目的** 确认模型的下一轮也有自己的 `turn_start`。
- **怎么测** 受控模型第一轮返回一次 `read` 调用，工具返回测试文本，第二轮返回纯文字答复。记录 `turn_start`、`context` 和模型收到请求的顺序。检查两轮各有一次 `turn_start`，每轮的 `turn_start` 都发生在对应的 `context` 和模型请求之前。

<a id="case-05"></a>

### 05 `context` 在模型请求前修改该轮消息副本

- **类型** 会话集成测试，使用受控模型。
- **目的** 确认 `context` 的输出用于当轮模型请求，历史保留正式用户消息。
- **怎么测** 发送 `原始输入`。测试扩展在 `context` 中把当前请求的消息副本改成 `本轮输入`。检查回调本轮触发一次且发生在模型收到请求前。模型收到 `本轮输入`，重新读取会话历史时用户消息仍是 `原始输入`。
- **异常补测** 在同一事件后面追加三个回调。第一个修改消息后抛错，第二个返回超过容量的消息，第三个应仍读到 `本轮输入`。检查服务记录前两项错误并按最后有效消息发送。

## 工具执行

<a id="case-06"></a>

### 06 `tool_call` 在文件编辑前拦截受保护路径

- **类型** 网页端到端测试，使用真实模型和原版 `protected-paths.ts`。
- **目的** 用实际文件状态证明执行前 Hook 生效，并把拒绝结果对应到原工具调用。
- **怎么测** 将原版扩展放入测试用个人扩展目录，重启服务。普通权限下在网页给真实模型发送请求，要求用 `edit` 把临时工作区 `.env` 的 `DEMO=before` 改成 `DEMO=after`，并在同一任务修改 `README.md` 的测试内容。核对真实模型确实分别发出了两个文件的 `edit` 调用。针对 `.env` 的工具结果按原调用编号返回扩展拒绝原因，文件内容仍为 `DEMO=before`，`README.md` 已改动。模型未发出目标调用时，该次运行缺少验收证据。

<a id="case-07"></a>

### 07 `tool_result` 在结果交付前改写内容和状态

- **类型** Agent 与会话集成测试，使用受控模型和工具。
- **目的** 确认实际执行结束后才运行 `tool_result`，改写结果用于后续通知和模型请求。
- **怎么测** 受控模型发起一个测试工具调用，工具返回 `原结果` 并报告成功。测试扩展在 `tool_result` 中读取原结果，再返回 `扩展改写后的结果` 和 `isError: true`。检查该回调在工具真正退出之后触发一次，`tool_execution_end`、会话保存结果、网页读取的结果和下一轮模型请求都与同一个调用编号对应，并使用改写后的内容和失败状态。若供应商协议通过工具结果文本表达状态，检查该请求中的失败语义。

<a id="case-08"></a>

### 08 `tool_execution_end` 在调用被拦后仍触发一次

- **类型** Agent 集成测试，使用受控模型和工具。
- **目的** 确认执行前拦截也会产生一次对应的结束通知。
- **怎么测** 受控模型发起一次工具调用，测试扩展在 `tool_call` 返回拦截并给出原因。记录工具执行次数和 `tool_result`、`tool_execution_end` 次数。检查工具和 `tool_result` 均为零次，`tool_execution_end` 在拦截结果确定后触发一次，携带原调用编号及对应的拒绝结果。

## 任务与会话收尾

<a id="case-09"></a>

### 09 `agent_before_settle` 在回复保存后请求续跑

- **类型** 会话与存储集成测试，使用受控模型和工具。
- **目的** 确认扩展看到的是已经保存的回复和工具结果，并能在原任务里请求续跑。
- **怎么测** 发起一次会先调用工具、再给出文本答复的任务。第一次进入 `agent_before_settle` 时，从会话库读回工具结果和完成的文本答复。回调追加「再核对一次」并请求续跑。检查模型收到追加指令，下一轮沿用原任务编号，会话仍处于进行中。第二次到达收尾点时，检查新回复已保存，回调结束后进入最终收尾。

<a id="case-10"></a>

### 10 `agent_settled` 在停止收尾后触发一次

- **类型** HTTP 与会话集成测试，使用受控模型。
- **目的** 确认停止任务走同一套终态通知，网页能够在收尾完成后收到空闲状态。
- **怎么测** 启动一个处于生成中的任务，发出针对该任务编号的停止请求。用测试扩展记录 `agent_before_settle` 和 `agent_settled`。检查中止流程先确定终态，`agent_settled` 触发一次并收到中止信息，完成后才向网页发布空闲并完成停止回执。`agent_before_settle` 的计数为零。

<a id="case-11"></a>

### 11 `session_shutdown` 在会话任务收尾后释放资源

- **类型** 本地服务集成测试，使用受控模型和测试资源。
- **目的** 确认服务关闭时，会话仍可通过 `session_shutdown` 完成本次清理。
- **怎么测** 在已初始化的会话里启动一项可中止的任务。测试扩展让 `session_shutdown` 关闭一个带释放标记的资源。调用本地服务关闭，记录任务收尾、`session_shutdown` 和关闭完成的顺序。检查任务先收尾，`session_shutdown` 针对该会话触发一次，服务在资源释放标记已写入后结束关闭。

## 个人目录与会话注册

<a id="case-12"></a>

### 12 服务从个人目录自动发现扩展

- **类型** 本地服务集成测试。
- **目的** 确认个人目录是首版扩展来源。
- **怎么测** 在测试用个人扩展目录放入一个直接入口和一个有 `index.ts` 的子目录。另在测试工作区放入一个项目扩展，并让每个入口写不同的标记。启动服务并打开该工作区的会话，检查两项个人入口已经加载并初始化，项目入口的标记没有出现。

<a id="case-13"></a>

### 13 加载保留目录和包声明顺序

- **类型** 加载及回调分发集成测试。
- **目的** 确认目录读取结果经过加载、会话初始化和事件分发时顺序一致。
- **怎么测** 给加载器提供已知的目录条目顺序，其中含一个独立扩展和一个含两个入口的包。故意让目录返回顺序及包声明顺序与名称排序不同。各入口为同一个事件登记可区分的回调。检查入口加载和回调执行均按目录返回顺序及包内声明顺序。

<a id="case-14"></a>

### 14 一个入口加载失败后服务仍可用

- **类型** 本地服务集成测试。
- **目的** 确认单个文件加载错误可定位，其他扩展仍可工作。
- **怎么测** 个人目录中放入一个默认导出为对象的无效入口，以及一个能登记 `input` 的有效入口。启动服务，核对错误包含无效入口路径和原因。发送普通消息，检查有效入口的回调运行并收到会话成功回执。

<a id="case-15"></a>

### 15 两个会话独立初始化扩展状态

- **类型** 会话集成测试，使用受控模型。
- **目的** 验证每个会话分别运行扩展入口，并保留自身状态。
- **怎么测** 扩展在入口函数中定义从 0 开始的计数器，每次 `input` 加 1 并记录会话编号。同时创建两个会话，各发送两次消息。核对两个会话分别得到 1、2，一个会话的提交不改变另一个会话的计数。

<a id="case-16"></a>

### 16 入口抛错后撤销该扩展的登记

- **类型** 会话扩展集成测试。
- **目的** 确认初始化失败后的部分登记不会生效。
- **怎么测** 扩展先登记一个 `input` 回调，再抛错退出入口。另一个扩展成功登记该事件。发送消息后检查服务记录失败扩展的路径和原因，只有成功初始化的回调被执行。

## 权限、中止与停用

<a id="case-17"></a>

### 17 执行前回调返回后复查最新权限

- **类型** 会话和工具执行集成测试，使用受控模型。
- **目的** 确认等待 `tool_call` 时切到只读，已经提出且尚未执行的写操作仍会受新权限管控。
- **怎么测** 普通权限下令模型发出 `edit`。让 `tool_call` 暂停，切换该会话为只读，再放行回调。检查工具未执行、文件内容保持原样，工具结果携带原调用编号和权限拒绝原因。

<a id="case-18"></a>

### 18 等待执行前回调时停止可跳过工具

- **类型** 会话和工具执行集成测试，使用受控模型。
- **目的** 确认执行前的回调收到停止信号，回调收尾后跳过工具。
- **怎么测** 工具调用进入异步 `tool_call` 并保持等待后，发出停止请求。检查回调先收到中止信号，停止请求仍在等它退出。放行回调清理后，核对工具调用次数为零，会话结束当前任务，停止请求返回。

<a id="case-19"></a>

### 19 移出保护扩展并重启后可编辑测试文件

- **类型** 网页端到端测试，使用真实模型。
- **目的** 验证把扩展移出个人目录并重启后，文件保护实际停用。
- **怎么测** 完成案例 06 后，把 `protected-paths.ts` 移出测试用个人扩展目录并重启同一个测试服务。在普通权限下从网页重新请求用 `edit` 把测试用 `.env` 的 `DEMO=before` 改为 `DEMO=after`。核对模型确实发出 `edit`，工具结果成功配对，磁盘读回 `DEMO=after`。

<a id="case-20"></a>

### 20 执行前回调报错时拦截该次调用

- **类型** 会话和工具执行集成测试，使用受控模型。
- **目的** 确认 `tool_call` 执行异常时保留工具调用的拒绝记录。
- **怎么测** 在普通权限下令模型发出写工具调用，分别让执行前回调抛出测试错误或返回非法类型的 `block`。核对之后的执行前回调、工具执行和 `tool_result` 次数均为零。日志包含扩展路径、`tool_call`、原因及该次调用编号，工具结束通知和模型接收的拒绝结果均沿用原调用编号。

## 提交结果与动态工具

<a id="case-21"></a>

### 21 首发由扩展处理时停留在草稿

- **类型** 网页端到端测试，使用受控模型。
- **目的** 确认「已处理」回执对应现有首发流程，扩展提示可见，草稿保持未正式保存。
- **怎么测** 新会话选择可用模型后发送 `ping`。测试扩展由 `input` 直接处理并提示 `pong`。检查输入框在回执到达后清除本次文本，页面提示 `pong`，侧栏仍没有新会话，历史没有新增用户消息，模型调用为零。

<a id="case-22"></a>

### 22 会话新增工具可在下一轮声明并执行

- **类型** 会话与工具执行集成测试，使用受控模型。
- **目的** 确认会话中登记的工具定义和执行函数成对进入下一轮。
- **怎么测** 在第一轮工具结果的回调里注册一个独立名称的测试工具。受控模型读取下一轮的工具声明后请求调用新工具。检查第一轮的工具声明尚未出现它，下一轮声明含参数定义，工具收到了对应参数并把结果回填到原调用编号。

## Agent 运行、消息与工具准备

<a id="case-23"></a>

### 23 `agent_start` 在续跑的首轮前触发

- **类型** Agent 与会话集成测试，使用受控模型。
- **目的** 确认首次运行和一次独立续跑各有自己的开始通知。
- **怎么测** 提交一项任务，让测试扩展在首次 `agent_before_settle` 追加有效指令并请求续跑。记录本次任务编号、`agent_start`、`turn_start` 和模型请求。检查同一任务共有两次 `agent_start`，每次都发生在对应一段运行的第一轮 `turn_start` 和模型请求之前。

<a id="case-24"></a>

### 24 `agent_end` 在内置压缩恢复前触发

- **类型** 会话集成测试，使用受控模型和压缩结果。
- **目的** 确认一次运行的结束通知先于会话的恢复动作。
- **怎么测** 在有可压缩历史的会话启动任务。让首次普通模型请求返回上下文超限，受控摘要请求成功，恢复后的模型请求返回最终回答。检查第一次 `agent_end` 先于溢出压缩，携带首次运行产生的消息。恢复运行结束后再次触发 `agent_end`，消息属于恢复运行。整个任务只在最后触发一次 `agent_settled`。

<a id="case-25"></a>

### 25 `message_start` 为每条正式消息触发一次

- **类型** 会话集成测试，使用受控模型和工具。
- **目的** 确认正式用户消息、助手消息和工具结果都有可观察的开始时点。
- **怎么测** 提交一条消息，让模型先调用一个测试工具，再生成文字答复。按消息标识记录 `message_start`。检查正式用户消息、两条助手消息和一个工具结果各有一次对应通知。助手消息的开始通知先于该消息的流式更新。

<a id="case-26"></a>

### 26 `message_update` 随助手消息增量触发

- **类型** Agent 与会话集成测试，使用受控模型流。
- **目的** 确认回调随当前助手消息的流事件通知，且可读取当时的部分内容。
- **怎么测** 让模型连续发送两段文字增量「早」和「上」。逐段读取 `message_update` 中的消息快照和流事件。检查两个 `text_delta` 通知按顺序到达，快照依次包含「早」和「早上」，回调返回值未改动最终的助手消息。

<a id="case-27"></a>

### 27 `tool_execution_start` 在工具拦截前触发

- **类型** Agent 工具执行集成测试，使用受控模型和工具。
- **目的** 确认进入执行准备的调用先发出开始通知，即使稍后被拦截。
- **怎么测** 模型发出一次路径为 `.env` 的 `edit`，测试扩展在 `tool_call` 返回拦截。检查 `tool_execution_start` 携带原编号、工具名和原始参数，先于 `tool_call` 触发一次。调用随后收到配对的 `tool_execution_end`，实际执行次数和网页的工具执行中通知均为零。

## 压缩与模型选择

<a id="case-28"></a>

### 28 `session_compact` 在摘要保存生效后触发

- **类型** 会话与存储集成测试，使用受控摘要模型。
- **目的** 确认扩展在收到成功通知时可以查到已生效的摘要。
- **怎么测** 在有可压缩历史的会话执行 `/compact`，受控模型返回合法摘要。在 `session_compact` 回调里读回存储和有效上下文，检查均使用同一份新摘要。检查事件只触发一次，原因是手动压缩。

<a id="case-29"></a>

### 29 `session_compact_failed` 在失败或中止结果确定后触发

- **类型** 会话与存储集成测试，使用受控摘要模型。
- **目的** 确认压缩的失败与中止通知可区分，原有效上下文继续使用。
- **怎么测** 对有可压缩历史的会话执行 `/compact`，分别让受控摘要请求失败和在等待期间中止。两次运行各触发一次 `session_compact_failed`。核对通知发生时压缩记录已确定为失败或中止，事件中的错误原因或中止标记和该次结果一致，上一份有效上下文仍在使用。

<a id="case-30"></a>

### 30 `model_select` 仅在模型实际变更后触发

- **类型** 模型选择与会话集成测试。
- **目的** 确认回调读取的是成功保存后的模型变化。
- **怎么测** 在已有会话把可用模型 A 切换为可用模型 B，再次提交相同的 B。检查只出现一次 `model_select`，旧值为 A、新值为 B，回调执行时可以从存储读到 B。

<a id="case-31"></a>

### 31 `thinking_level_select` 仅在推理强度实际变更后触发

- **类型** 模型选择与会话集成测试。
- **目的** 确认模型相同时，推理强度仍可独立触发通知。
- **怎么测** 在已有会话选择支持两档强度的模型，把强度从第一档改为第二档，再次提交相同设置。核对存储已采用第二档，`thinking_level_select` 只触发一次并携带两档值，`model_select` 的计数为零。

## 供应商响应

<a id="case-32"></a>

### 32 `provider_stream_event` 在流数据归一化前触发

- **类型** 模型适配器集成测试，使用受控模型流。
- **目的** 确认两个模型接入路径都能把已解析的数据块交给扩展观察。
- **怎么测** 通过通用 Pi 适配器和独立 DeepSeek 适配器分别发送受控请求。每条路径让供应商返回顺序可辨认的数据块。检查通知与原数据块一一对应，在对应 SI 统一流事件之前到达，携带正确的供应商、协议、模型和数据。模型对外输出继续使用既有的统一格式。

<a id="case-33"></a>

### 33 `after_provider_response` 在读取响应流前触发

- **类型** 模型适配器集成测试，使用受控 HTTP 响应。
- **目的** 确认有可用 HTTP 响应元数据时，扩展先看到响应状态和头，再看到流数据。
- **怎么测** 在能公开 HTTP 元数据的路径返回 HTTP 200、测试响应头和一段可读取的流，记录适配器首次消费响应体的时点。检查 `after_provider_response` 对该响应只触发一次，状态和头与响应一致，回调早于首次消费及第一个 `provider_stream_event`。复用现有受控 Google 请求，验证其正常流转且该 HTTP 通知计数为零。

## 首发准备与服务关闭

<a id="case-34"></a>

### 34 首发 Hook 等待期间关闭服务

- **类型** 本地服务与 HTTP 集成测试，使用受控模型和临时会话库。
- **目的** 首条正式消息和任务尚未保存时，关闭能通知正在等待的回调，并等其退出后再释放会话资源。
- **怎么测** 调用 `POST /api/sessions/start`，让测试扩展在 `before_agent_start` 中等待。确认首发尚未收到成功回执后调用服务的 `close()`。扩展记录 `ctx.signal` 的中止事件，随后继续等待测试解除。检查关闭仍未完成、`session_shutdown` 尚未触发且会话库仍可读。解除等待时让回调正常返回一项有效的改写，确认返回值也无法让已关闭的会话开始任务。
- **预期** 顺序为收到中止信号、`before_agent_start` 退出、`session_shutdown` 完成、服务关闭完成。`session_shutdown` 对该草稿会话恰好触发一次。首发未收到成功回执，模型调用次数为零。重新读取临时库，确认没有该草稿的正式会话、用户消息或任务。 [关闭流程](./feature4-Hook机制与文件保护技术设计.md#feature4-close-pending-submit)

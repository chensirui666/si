# 技术设计文档 skill 设计

状态：用户已批准；最后补充已确认的关键决策定义。

## 目标与范围

在不同仓库中，把用户需求变成用户能够理解、评审并逐步批准的技术设计文档。工作范围截至文档通过，不包含产品实现。输出个人 skill `technical-design`，参考源码遵循当前项目约定与用户材料，不固定参考项目。

## 已选方式

考虑过按文档章节逐章确认与按实际功能模块逐个确认。用户选择后者：每个模块连贯讨论职责、数据、接口和失败处理，批准后整理到固定模板，最后整体检查跨模块一致性。代价是需要维护模块内容与文档章节的对应关系。

## 三阶段

1. 需求确认：阅读材料，询问未明确的功能问题，复述需求理解，以用户明确批准为通过条件；不另设阻止用户批准的标准。
2. 调研与关键决策：核对当前仓库，查找本地相似实现，追踪调用、数据、失败路径与相关测试；解释适用性、差异和风险。每项重要选择说明做法、优劣、建议和依据，由用户确认。
3. 按功能模块讨论：逐个说明职责、数据交互、接口、失败处理和验证方式；仅将批准内容写入文档。整理后整体检查接口、数据和失败行为是否一致，交由用户批准整份文档。

## 关键决策定义

按对系统的影响识别：不同方案会改变功能行为、模块职责、数据存储和流转、接口约定或失败处理，就是需要用户参与的设计选择。即使方案清楚、技术成熟、只有一个合理做法，也要解释并确认。

技术事实由 Agent 调研；命名和普通函数内部写法由 Agent 处理。已批准且未变化的决定直接沿用，避免重复询问。

## 回退

后续发现与已批准需求或决策不一致时，指出冲突、影响范围和待重决事项，暂停受影响内容，重新请用户决定。保留未受影响的批准。

## 文档约束

随附用户提供的完整六章 Technical Design Template，不压缩替换。源码结构使用代码，设计理由使用中文；区分已有、拟修改、拟新增和已验证内容。表格仅可用于拟增加文件，图与正文不重复叙述。

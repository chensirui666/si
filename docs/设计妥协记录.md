## 1. 会话暂保存在后端内存

- **妥协点**　本期会话暂保存在内存。后端进程重启后，已发送的聊天、工具记录、压缩摘要和任务状态无法恢复。
- **当前做法**　每个会话的聊天、工具记录、压缩摘要和运行状态由自己的 `AgentSession` 持有。网页切换时只换订阅，刷新或重连后通过 WebServer 取回该会话的内容和状态，再接收增量。关闭网页时已经开始的任务继续运行。同一浏览器按会话编号保存已开始会话的草稿，两个新会话入口共用一份首发草稿。
- **设计沿革**　原 Feature1 仅验证输入、发送与显示，由 `ChatPage` 保存页面消息，刷新后清空。原前三步合并后，用户确认将消息与运行状态转到后端 Agent，原草案 Conversation 的运行协调职责一并归入 Agent。第七步增加压缩记录，第八步用 `AgentSession` 隔离各会话。
- **重启边界**　工作区登记和凭据已保存到本机。原会话随进程结束，网页提示原会话不可用。
- **更好的做法**　将对话记录与运行状态保存到本机磁盘，重启后读取并明确标记中断状态。草稿的恢复另按实际需求设计。
- **解决时机**　第十步按第八步的会话编号保存各自原始历史和第七步的压缩记录。第九步先加载项目说明作为启动上下文。
- **来源**　[Feature8 技术设计](../planning/里程碑1/feature8/feature8-基础Session机制技术设计.md)、[单会话聊天规划](../planning/里程碑1/README.md)、[原 Feature1 技术设计 §4.3](./里程碑1/feature1/feature1-基本聊天页面.md#43-草稿归-lexical发送后的消息归-chatpage)。

## 2. 暂用 Vite 开发服务提供页面（已确定替代方案，待实现）

- **妥协点：** 当前入口依赖前端开发服务，还没有与本地 Agent 服务组成完整应用入口。
- **当时的设计：** 用现有 Node.js 和 npm 运行 Vite，浏览器打开本机开发页面。
- **为什么这样设计：** Feature1 尚无后端，不必为展示页面先建设完整本地服务。
- **已确认的替代设计：** 日常由一个 Node.js 服务在同一本机地址提供构建后的网页、HTTP 接口和 WebSocket；开发时保留 Vite 提供页面及自动更新，并转发业务 HTTP 和 WebSocket 请求到 Node.js 后端。日常网页修改后需要重新构建。
- **解决时机：** 单会话聊天阶段一实现并验收上述入口后解决；目前仅已确认技术设计，现有页面仍使用 Vite。
- **来源：** [Feature1 技术设计 §4.1](./里程碑1/feature1/feature1-基本聊天页面.md#41-使用-react--typescript--vite在-web-内组织网页代码)、[当前单会话聊天规划](../planning/里程碑1/README.md)；用户于 2026-10-28 确认“日常一个服务，开发保留 Vite”。

## 3. 提交和消息内容暂时只表达普通文字

- **妥协点：** 字符串不能完整表达引用目标，当前消息类型也只有用户角色。
- **当时的设计：** 输入接口为 `onSend(text: string): boolean`，消息使用 `{ id, role: 'user', text }`；普通用户文字按原文展示。
- **为什么这样设计：** Feature1 没有模型回复和引用标签产生的数据，只需提交和展示文字。虽然已经选用 Lexical，仍不提前建立引用数据结构。
- **已确认的替代设计：** 模型回复采用 Pi 式 `text`、`thinking`、`toolCall` 有序内容块，包含工具调用 ID、名称和结构化参数；快照引用的共享消息结构在阶段一建立，真实调用、完整模型事件与展示在阶段三接入。模型正文按 Markdown 展示，非空 thinking 独立展示且默认收起、可展开，用户消息仍按原文展示。发送改为立即清空并显示临时气泡，以临时展示编号与后端正式消息对应。上述设计尚未实现。
- **更好的做法：** 引入对应功能时，按实际需要扩展消息角色、结构化内容和提交接口；引用标签应携带目标信息，不能只保存可见名称。异步服务的接收结果与后续运行结果也要分别设计。
- **解决时机：** 单会话聊天阶段三接入 AI 回复、运行状态与异步提交；引用标签仍在其对应功能阶段一并设计编辑内容、提交接口与消息展示。
- **来源：** [Feature1 技术设计 §4.5](./里程碑1/feature1/feature1-基本聊天页面.md#45-消息暂用-idrole-和-text-表达)、[§4.4](./里程碑1/feature1/feature1-基本聊天页面.md#44-用同步布尔回调表达本步的接收结果)。

## 4. 生成期间暂不支持排队发送

- [ ] **后续待办：** 支持生成期间继续发送消息，由后端保留排队输入，当前回答结束后依次正常调用模型；补齐排队状态、处理顺序和队列取消规则。具体排期未定，不作为单会话聊天三个子阶段的完成条件。
- **妥协点：** 当前回答尚未结束时，用户可以编辑下一条草稿，但必须等待后才能发送。
- **本期设计：** 生成期间前端暂时禁用发送，后端对并发提交明确拒绝；完成或失败后恢复发送。禁用发送期间编辑的下一条草稿留在前端；实际发起提交后按[立即清空且失败不恢复](#5-提交失败后不自动恢复已清空的草稿)的规则处理。该规则只限制生成中的并发，不按消息内容或编号去重。
- **为什么这样设计：** 用户明确选择先完成基础单会话流式聊天，暂不增加消息队列及其界面状态，以控制本期复杂度。
- **更好的方向：** 采用用户期望的 B：允许提前提交下一条消息，后端按顺序执行，而不是同时并发请求模型；相关状态与取消行为在后续队列功能中一起设计。
- **解决时机：** 后续消息输入体验迭代，具体排期未定；开始引入排队输入时重新评估并替换本期限制。
- **来源：** 用户于 2026-10-28 确认本期采用 A，并要求记录 B 为后续待办；见[单会话聊天规划](../planning/里程碑1/README.md)。该条记录设计选择，尚未实现到当前页面。

## 5. 提交失败后不自动恢复已清空的草稿

以下保留 Feature2 设计时的取舍。Feature8 首发在接收确认前保留原文。已有会话明确拒绝提交后，仅在原会话没有新草稿时恢复原文。见[当前使用说明](development.md#运行项目)。

- **妥协点：** 用户发起发送后立即清空输入框；提交失败时不自动将原内容恢复到输入框。
- **本期设计：** 沿用 B 的立即清空与待发送消息展示，后台等待 HTTP 接收确认；失败时显示明确错误，不恢复草稿、不自动重发，不覆盖用户正在编辑的新草稿。失败或未确认接收的临时气泡在当前网页内存中保留并标记状态，刷新后不恢复这些本地条目；后端已接收的用户消息与失败模型回复仍按当前对话规则保留，不受这项草稿简化影响。
- **为什么这样设计：** 用户在核对 Pi 与 dsh 的清空时机后，明确选择立即清空，并要求省去失败后的草稿恢复，以简化本期。
- **更好的方向：** 如后续需要改善发送失败体验，参考 dsh 恢复失败草稿，并保护用户新输入的内容；具体恢复交互届时讨论。
- **解决时机：** 后续确有失败内容找回需求或重做提交体验时重新评估，当前不承诺恢复功能的排期。
- **来源：** 用户于 2026-10-28 明确采用 B，并要求不支持失败后恢复原内容；见[单会话聊天规划](../planning/里程碑1/README.md)。当前记录为已确认设计，尚未实现。

## 工具参数 JSON 暂不自动修复

- **妥协点：** 参数文字内存在非法转义或未转义控制字符时，部分 Pi 能有限修复的内容，本项目会记录为解析失败。
- **当前做法：** 已在 Feature2 阶段三实现：空参数文字按 `{}` 接收；非空文字严格解析为 JSON 对象。失败时保留调用，以 `argumentsError` 记录原因和原始参数，不修复转义、不补齐截断结构；具体工具参数校验仍留给执行前处理。
- **原因：** 用户明确选择先用标准解析完成本期后端工具接入，减少兼容分支，并保留清楚、可复查的失败信息。
- **更好的方向：** 真实数据证明有必要时，评估引入 Pi 对字符串转义和控制字符的有限修复；继续拒绝结构截断，不推测字段或补齐任务内容。
- **解决时机：** 后续真实模型调用反复因上述可修复问题失败、影响正常使用时重新讨论；本期不自动启用修复。
- **来源文档与章节：** [Feature2 Model 参数解析边界](./里程碑1/feature2/feature2-单会话流式聊天技术设计.md#key-model-stream)。该选择已在原设计确认，并已由 Feature2 实现；2026-11-04 复跑 Model 现有 46 项测试通过，包含严格解析案例。Feature3 仅设计尚缺的声明与请求接入，不再承载已实现的解析约定。

## 一批工具结果回填后结束本次任务（Feature6 已解除）

- **妥协点：** 模型收到工具结果后只能给出最终回答。需要依据结果继续操作时，由用户发起下一条消息。
- **当前做法：** 首轮模型给出一批调用，Agent 依次执行。第二次模型请求携带调用与结果，只用于回答。Feature4 已实现。
- **原因：** 第四步分别验证八种工具的执行及结果回填，保持可独立定位的验收范围。
- **更好的方向：** 沿用 Pi 的循环，让模型依据工具结果继续提出后续调用。
- **解决时机：** 里程碑一第六步引入连续工具决策时重新评估。
- **重新评估状态：** Feature6 已确认采用 Pi 连续决策、同批默认并行及截断恢复 A，见 [Feature6 技术设计](./里程碑1/feature6/feature6-ReAct循环技术设计.md) §3、§4；已于 2026-11-08 实现、合并 main 并完成主目录复验，当前主干可连续决策，原限制已解除。验收见[记录](./里程碑1/feature6/feature6-验收记录.md)。
- **来源文档与章节：** [Feature4 技术设计](./里程碑1/feature4/feature4-工作区选择与四工具执行.md) §4.3、§4.11。

## read 图片支持延后

- **妥协点**　通过 `read` 读取截图等图片的任务留到后续能力扩展。
- **当前做法**　第四步交付 UTF-8 文本读取，工具结果、模型回填和网页结果使用文本。
- **原因**　当前应用的工具结果和模型转换都是文本结构。图片需要扩展内容类型、模型请求和网页展示。本期先验证八工具执行与结果回填。
- **后续方向**　参考 Pi 的结构化图片结果及 Chat Completions 附件转换，再验证模型能从本机图片读出内容。[Pi read](../pi/packages/coding-agent/src/core/tools/read.ts) · [Pi 模型适配器](../pi/packages/ai/src/api/openai-completions.ts) · [DeepSeek Vision](https://api-docs.deepseek.com/guides/vision/)

## 提交尚未确认时暂不可中止

- **妥协点：** 发送后主按钮切换为中止，但网页尚未收到后台运行状态时暂不可点击，不能保证中止尚未确认的提交。
- **已确认的做法：** 参照 dsh，根据后台运行状态启用中止；本项目在同一订阅更新中取得正式用户消息编号，再调用指定运行的中止接口。输入框始终可编辑，等待期间显示正在确认接收。
- **原因：** 目标定位需要已确认的运行身份，避免迟到或未确认请求影响其他运行；保留现有接收与订阅契约，不增加等待确认后自动发出中止的本地待办。
- **更好的方向：** 确有需求时，让尚未确认的提交也能被明确识别并请求取消，同时如实区分接收、取消和未确认结果。
- **解决时机：** 弱网络或实际接收等待反复影响中止操作，或用户明确要求支持提交确认前中止时重新评估；本期不承诺该能力。
- **来源：** 用户于 2026-11-07 要求参考 dsh，并确认网页模块；见 [Feature5 技术设计 §4、§5](./里程碑1/feature5/feature5-用户停止当前调用技术设计.md)。该边界已在 Feature5 实现、验收并合并 main。

## 压缩摘要只读取长工具结果的头尾

- **妥协点：** 仅存在于长结果中间的事实可能无法进入摘要，影响后续续做。
- **已确认的做法：** 摘要输入中，超过 2,000 字符的单条工具结果保留前 1,500 和后 500 字符，并标明中间省略；原始记录和近期保留原文不截取。该选择已在 Feature7 实现，见其验收记录。
- **原因：** 控制摘要请求大小，沿用 Pi 的单条预算，并按用户要求兼顾头部和尾部信息。
- **更好的方向：** 实际任务需要时评估扩大预算、按结构抽取或分段摘要，不承诺摘要无损。
- **解决时机：** 两次压缩验收或实际任务频繁因结果中部缺失而答错、漏约束时重新评估。
- **来源：** 用户于 2026-11-08 明确指定“前1500字符和后500字符”；见 [Feature7 技术设计 §3.1、§4、§5](./里程碑1/feature7/feature7-基础上下文压缩技术设计.md)。

## 对话容量与三类分布暂用近似统计

- **妥协点：** 页面圆环和分布不是精确计费数据；三类估算之和不必等于参考总占用，中文和 JSON 可能低估。
- **已确认的做法：** 依用户指定参考 dsh，总占用使用最近实际输入加有效内容变化估算，系统提示词、工具定义、对话消息独立估算并标注近似。日常不为统计额外调用模型，严格真实前后对照只用于受控验收。该口径已在 Feature7 实现，实际用量与估算分别展示。
- **原因：** 当前服务商只返回总输入用量，没有这三类真实分项；用现有请求和本地估算即可及时展示变化。
- **更好的方向：** 有可靠本地计数或服务商分项能力时改善精度，仍保留实际用量与估算的区别。
- **解决时机：** 实测反复明显低估并影响压缩时机，或服务商提供可靠计数能力时重新评估。
- **来源：** 用户于 2026-11-08 指定 dsh 并确认容量流程；见 [Feature7 技术设计 §3.2、§3.6、§4](./里程碑1/feature7/feature7-基础上下文压缩技术设计.md)。
